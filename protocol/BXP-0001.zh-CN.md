# BXP-0001：BoundX 任务边界协议

## 摘要

BoundX 任务边界协议（BXP）定义有原文证据的任务边界中间表示，以及作用于该表示的确定性计算。核心是输入 I、交付 O、动作 A、责任授权 P、资源 R、版本依据 V、完成停止 C，以及独立的禁止边界 B。

BXP 不规定自然语言编译器必须如何推断要素；它规定如何表达抽取结果、保留未知、执行类型化计算，并在不作业务裁决、不授予执行权的前提下返回发现。

## 1. 当前地位与规范用语

本文件与 [英文规范](BXP-0001.md) 同版本、同节编号维护，是便于中文评审的译本；发生差异时以英文草案为准。它不是 IETF RFC、已采用行业标准、认证计划或发布授权。

英文 MUST / MUST NOT / REQUIRED 对应“必须／不得／必需”，SHOULD / SHOULD NOT 对应“应／不应”，MAY / OPTIONAL 对应“可以／可选”，均指本草案的要求等级。

符合性声明必须包含具体协议版本、符合性等级和套件版本，不能笼统宣称“符合 BXP”。

## 2. 协议范围

BXP 规范：

1. 类型化、证据绑定的 7+1 任务边界 IR；
2. 确定性结构校验；
3. 区间、类型集合、跨阶段交接、强制前置依赖图和命题一致性计算；
4. 彼此独立的校验、完备性和一致性结果；
5. 不裁决的发现以及扩展规则；
6. 版本化一致性测试向量。

BXP 不规范某个 NLP 模型、解析器、语法或词库，也不替代企业身份、授权、流程和生命周期系统，不执行任务、验收、发布或恢复。计算不能证明自然语言已被正确理解，不能证明任务安全、合法、有价值或已经完成。

## 3. 7+1 核心模型

`boundx-task/v1` 冻结以下标识及含义：

| 标识 | 名称 | 规范含义 |
|---|---|---|
| I | 输入范围 / Input | 任务涉及的对象、数据、系统或总体。 |
| O | 交付结果 / Output | 明示的交付物或外部可观察结果。 |
| A | 动作 / Actions | 由主体、效果和目标表达的允许或要求操作。 |
| P | 责任授权 / People | 负责、执行、观察和审批主体；表达授权信息不等于授予执行权。 |
| R | 资源 / Resources | 数量限制、预算、容量与阈值。 |
| V | 版本依据 / Version and Provenance | 适用版本、制度、证据来源和时间基线。 |
| C | 完成停止 / Completion | 完成、停止和升级条件。 |
| B | 禁止边界 / Forbidden Boundary | 被禁止的效果、目标或组合及其条件和例外。 |

B 独立于 R。“不得超过 120 秒”是 R 的数值上界；“不得删除生产数据库”是 B 的行为边界。

每个要素桶必须明确标为：

- `resolved`：至少存在一条有证据的确定条目；
- `unresolved`：存在候选，但无法证明唯一解释；
- `absent`：来源或提交的投影中没有该要素。

不得用默认值、行业刻板映射或模型置信度把后两者静默改成 `resolved`。

## 4. 原文证据合同

每个确定或待消歧条目必须包含原文 Span：

- 来自指定来源的精确引文 `quote`；
- 按 Unicode **码点**计数、左闭右开的 `start` 与 `end`；
- 可选 `source_id`，省略表示保留 ID 为 `task` 的主来源。

必须满足 `0 <= start < end <= codePointLength(text)`，对应切片必须等于引文。不得截断越界下标后继续判定有效。必须拒绝未配对代理项；比较和摘要前不得做 Unicode 归一化、换行转换、去空白或翻译。中文、英文、混合文本遵循同一合同；UTF-16 代码单元和 UTF-8 字节偏移都不是码点偏移。

可选 `sources` 最多声明 16 份附加文档，每份必须含唯一 `id`、`kind`（`policy | clarification | reference`）、非空 `version`、`language`、精确 `text` 和 `digest`（该文本 UTF-8 字节的 SHA-256 小写十六进制）。不得重定义 `task`。来源引用不存在或摘要不符时 IR 无效。

文档由调用方本地提供；计算器不得自动访问制度 URL 或选择更新版本。摘要证明内容身份，不证明真实性、制度适用性或授权。原文证据只证明提交解释的出处，不证明该解释唯一或正确。归一化必须保留原文，应记录语义包及产生归一化值的规则或模型版本。

## 5. 规范任务信封

任务必须完整满足 `schemas/boundx-task-v1.schema.json`，必需字段为 `schema`、`protocol_version`、`task_id`、`source`、`profile`、`elements`、`constraints`、`extensions`。例如：

```json
{
  "schema": "boundx-task/v1",
  "protocol_version": "0.3.0-draft.1",
  "task_id": "example-001",
  "source": { "language": "zh-CN", "text": "..." },
  "profile": {
    "id": "org.boundx.core-7plus1",
    "required_elements": ["I", "O", "A", "P", "R", "V", "C", "B"]
  },
  "elements": {
    "I": { "status": "absent", "entries": [] },
    "O": { "status": "absent", "entries": [] },
    "A": { "status": "absent", "entries": [] },
    "P": { "status": "absent", "entries": [] },
    "R": { "status": "absent", "entries": [] },
    "V": { "status": "absent", "entries": [] },
    "C": { "status": "absent", "entries": [] },
    "B": { "status": "absent", "entries": [] }
  },
  "constraints": {
    "intervals": [],
    "target_sets": [],
    "handoffs": [],
    "dependencies": [],
    "logic": []
  },
  "extensions": {}
}
```

这是结构有效但内容不完备的信封，不是已明确的任务。`resolved` 空条目桶无效。

必须先执行完整 Schema 校验，再执行语义校验和计算。校验不得强制类型转换、注入默认字段或删除未知属性。任何无效输入都停止全部计算。条目 ID 在八个要素桶间全局唯一；具有 ID 的约束在各自集合内唯一。`normalized` 是可选的不透明生产者元数据，不是可执行逻辑；计算仅使用类型化 `constraints`。

### 5.1 显式计算作用域

可选 `scopes` 最多声明 128 个作用域，含唯一 `id`、有证据的 `description`、`identity_status`（`resolved | unresolved`）及 `evidence`。保留作用域 `task` 隐含存在，不得重定义。

每条类型化约束可以声明 `scope_id`；省略明确表示共同的任务级作用域，不代表推断阶段、主体同一性或条件。每个计算结果必须返回 `scope_id`。

引用未声明作用域属于无效输入。身份未明确作用域的约束必须跳过，并返回 `BXP.SCOPE.UNRESOLVED`；其他已明确作用域仍可计算。作用域只是调用方提交的状态切片，不是可执行条件语言。

本版不隐式把 `task` 约束继承到其他作用域，不计算跨作用域可满足性、阶段调度或制度优先级。生产者必须将适用的全局约束带证据显式投影至各相关作用域；适用性未知时必须保持未知，不得当成豁免。计算器不能证明投影完整或正确。

## 6. 确定性计算

### 6.1 Profile 完备性

令 `Required(profile)` 为 Profile 要求的要素，`Resolved(task)` 为状态确定且条目非空的要素：

```text
Deficit = Required(profile) minus Resolved(task)
```

差集为空只证明提交的 IR 覆盖 Profile 要求，不证明抽取正确或与原文语义等价。

### 6.2 区间代数

区间按 `(scope_id, subject, dimension, unit, domain)` 分类；只有五项完全相同才能求交。同一前四项不得混用整数域与实数域，否则无效。`domain` 为 `real`（默认数学域）或 `integer`。身份或换算未确定时，生产者不得提交确定键，应在相关要素中保留未明确证据。

输入端点只能是安全整数范围 `[-9007199254740991, 9007199254740991]` 内的 JSON 整数，或匹配 `^-?(?:0|[1-9][0-9]*)(?:\.[0-9]+)?$`、不超过 256 字符的十进制字符串。小数和更大数值必须使用字符串，不得包含指数、千位分隔、单位或前导加号。

必须精确比较十进制，不得使用二进制浮点舍入、epsilon 容差或隐式换算。无界仅用 `null` 表达，两端不得同时为空。

输出端点统一为规范十进制字符串：去掉小数末尾多余零和尾随小数点，零统一为 `0`。整数域闭端点用下界向上取整、上界向下取整；开端点用 `floor(lower)+1` 与 `ceil(upper)-1`，输出转为闭端点。为容纳极值进位，计算结果允许 257 字符。这些默认值描述提交的数学模型，不补造缺失任务事实。

交集下界取最大值，上界取最小值。下界大于上界，或相等但至少一端为开区间时，交集为空。不同量纲和未确认单位换算必须保持分离，不得因局部非空就声称相互兼容。

### 6.3 类型集合交集

请求目标和禁止目标必须共享声明的对象域、动作效果、主体范围及条件上下文：

```text
Overlap = RequestedTargets intersect ForbiddenTargets
```

交集非空是确定性冲突发现，不自动构成执行拒绝或授权决定。效果或对象域同一性未明确时，必须返回 `undetermined`。

### 6.4 跨阶段交接

交接必须声明生产阶段、消费阶段和制品类型：

```text
Available = DeclaredOutputs union ExternalInputs
Missing = RequiredInputs minus Available
```

非空缺口只证明提交任务包内缺少供给，不证明制品在系统外绝对不存在。制品同一性未解决时必须返回 `undetermined`，不得仅凭文件名相似认定同一。

### 6.5 强制前置依赖图

按作用域分别计算，只有明确标为 `prerequisite` 的边参与无环检查。参考关系、信息流和有界迭代不得被自动改写为强制前置边。

有向环表示提交的强制前置关系无拓扑顺序，不证明线上已经发生死锁。

### 6.6 命题一致性

`logic` 使用无量词布尔 AST。每条约束必须声明局部变量，公式及可选假设中的变量引用必须局部声明。省略假设表示布尔 `true`，不是补造业务许可。

同一已明确作用域中的全部公式与全部假设必须合取后一起求解；同名变量只在该作用域共享真值，不同作用域独立赋值。不得把相互矛盾的公式分到不同条目后逐条求解，从而掩盖合取冲突。

每个作用域最多 12 个不同变量；每棵 AST 深度最多 16（根为零）；整个任务所有公式及假设合计最多 4096 个 AST 节点。支持 `var`、`not`、`all`、`any`、`implies` 和布尔字面量。`all/any` 必须有 1–64 个操作数，`implies` 必须有两个。超限是无效，不是可满足，也不得静默截断。

已明确作用域返回 `satisfiable` 或 `unsatisfiable`；未明确作用域跳过并返回未明确发现。逻辑结果 `id = scope_id`，附排序后的 `constraint_ids`。无解时 `witness: null`；有解时按变量名排序，再以 `false` 先于 `true` 的字典序返回首个满足赋值。

无解仅证明给定归一化、状态切片和假设下无解；可满足不证明安全、授权、合法或现实可行。没有原文同一性证据或显式 Profile 规则时，不得把不同名称的主体、目标或效果合并成同一变量。

## 7. 结果信封与权力边界

结果必须符合 `schemas/boundx-result-v1.schema.json`，使用 `schema: boundx-result/v1`，分别表达：

- `validation`：`valid | invalid`；
- `completeness`：`complete | incomplete | unresolved | undetermined`；
- `consistency`：`consistent | inconsistent | undetermined`。

所有结果必须保持：

```json
{
  "business_decision": null,
  "execution_authorization": null
}
```

`source_digest` 是主来源精确 UTF-8 字节的 SHA-256 小写摘要，`source_digest_algorithm` 固定为 `sha-256:utf8`。`input_digest` 还必须按 §7.1 绑定整个提交 JSON，包括 Profile、作用域、来源、约束和扩展。摘要不是签名，不证明制度已被采用。各计算集合必须使用 Schema 定义的类型化结果对象。

聚合优先级是规范要求：

1. 输入无效：校验为 `invalid`，其余两轴 `undetermined`，全部计算数组为空。
2. 有效输入的完备性：必填要素有未明确则 `unresolved`，否则有缺项则 `incomplete`，否则 `complete`。
3. 有效输入的一致性：已算出任何冲突则 `inconsistent`；否则任一要素（含非必填）、作用域或计算身份未明确则 `undetermined`；否则 `consistent`。

**无关未知不得掩盖已经证明的冲突。** `consistent` 仅表示提交且已明确的计算未发现冲突，不证明抽取覆盖、跨单位兼容或现实可行。

任何符合性等级都不允许 BXP 替代任务授权方、负责人、审核人或外部审批系统。发现只描述计算事实、假设和缺失信息。

### 7.1 确定性序列化与诊断

输入摘要的规范序列化递归按 UTF-16 代码单元序排序对象键，保留数组次序、不输出空白；字符串、有限数值、布尔和空值使用 ECMAScript JSON 标量序列化，负零写为 `0`。对结果 UTF-8 字节求 SHA-256。对象插入顺序无语义意义，数组顺序有意义。

解码器必须在构造对象前拒绝重复 JSON 键；解析后的计算器无法恢复已丢弃键。本参考对象 API 接收已解码 JSON，不声称代替调用方解码器检测重复键。

Schema／前置限额失败返回单条 `BXP.IR.INVALID_ENVELOPE`。语义校验只返回首个无效发现，次序为来源、作用域、I/O/A/P/R/V/C/B，再按 intervals/target_sets/handoffs/dependencies/logic 集合与各自输入次序。有效结果发现按要素、未明确作用域、五类计算次序输出。

计算数组按输入次序或分组键首次出现次序输出。证据按完整 Span 相等去重并保留首次出现次序；单条输入证据列表仍最多 32 项，聚合发现证据最多 16384 项。发现的证据是支持上下文，不是最小无解核。

目标交集、交接可用／缺少集合、布尔变量名及约束 ID 按 UTF-16 代码单元序排序。前置图以排序节点和去重排序邻居进行深度优先遍历，维护访问中／已完成集合；遇回边输出当前环路径并重复起点，相同环数组按遇到次序去重。这是确定性环见证，不穷举全部图环。边数统计提交的强制前置边，包含重复边。

未提交任何依赖边时返回一个空 `task` 图；某作用域提交的边全部因身份未明确而跳过时，不返回该作用域图。

无效结果必须使用计算器支持的版本，不回显不支持的输入版本。合法长度（1–256 码点）的字符串任务 ID 保留，否则使用 `invalid-task`。JSON／Unicode／资源前置检查失败时，输入摘要取 JSON null 的摘要，任务 ID 使用 `invalid-task`，主来源摘要取空字符串摘要。其他无效输入仍摘要整个提交值；主来源缺失、非字符串或超长时，来源摘要同样取空字符串摘要。这些回退只是诊断，不宣称任务内容有效。

包括错误结果在内，每次输出都必须通过结果 Schema。冻结向量忽略对象键顺序，但比较数组顺序和全部值，包括固定英文诊断消息。中文／英文展示层可以根据稳定 `code`、`path`、状态及数值翻译显示；不得翻译或覆盖原文证据，也不得改写冻结线上信封。展示语言变化不是新协议版本。

数值解码器必须保留端点精度，或在舍入使原始数字看似成为合法安全整数之前拒绝该数值。对象计算器不能恢复调用方已舍入的数据；十进制字符串端点可避免这种损失。本参考对象 API 不是原始 JSON 传输层，也不声称提供保精度解析器。

## 8. 扩展与 Profile

I/O/A/P/R/V/C+B 的含义在 v1 中不得重定义。新增字段必须进入 `extensions`，使用反向域名命名空间，如 `com.example.risk-score`。实现可以忽略不理解的扩展，但转发同一个信封时必须原样保留。

Profile 可以选择必填要素、收紧证据及类型要求、注册行业词汇和同一性规则、要求命名空间扩展；不得降低证据完整性、消除未知、授予执行权或重定义核心语义。“第九要素”可以作为扩展存在；兼容性由行为合同而非宣传数字决定。

本参考计算器只实施提交的 `required_elements`，不会按 ID 自动加载任意 Profile、执行 `normalized` 元数据或激活语义包。生产者应在命名空间来源扩展中固定外部 Profile／语义包／规则的版本与内容摘要。命名空间或来源类型本身不代表可信。

L1 通用、L2 行业和 L3 企业仍是这一协议之上的生产者层，不能静默覆盖 B，也不能把制度来源当成执行授权。任务扩展参与输入摘要，但不复制到新计算结果的空 `extensions` 中；转发同一信封属于另一项 BXP-RELAY 义务。

## 9. 符合性等级

| 等级 | 要求 |
|---|---|
| `BXP-IR` | 能读取并校验规范任务与结果 Schema。 |
| `BXP-CALC` | 完整通过指定版本 BXP-CALC 套件的全部冻结向量。 |
| `BXP-EXTRACT` | 输出证据绑定候选并保留 unresolved/absent；单独评测。 |
| `BXP-RELAY` | 转发时保留未知命名空间扩展和核心字段。 |

自然语言抽取基准属于信息性评测，不是规范性计算向量。历史案例只能以 `calculation-pattern-only` 方式派生计算模式，不得宣称是原文语义翻译或抽取金标。

## 10. 安全与隐私

原文和租户语义包可能敏感，未经独立授权不得发送到外部模型或服务。日志应存摘要和有界证据，不应无限记录原文。

实现必须限制输入长度、集合规模、表达式深度及变量数，拒绝非有限数值、无效 Unicode 证据和不支持的算子。

本版 BXP-CALC 的解码 JSON 最多 100000 个值节点，嵌套深度最多 64（根为零），经紧凑 ECMAScript JSON 序列化后最多 2000000 UTF-8 字节；每个来源最多 100000 码点。参考前置检查还拒绝键与字符串合计超过 2000000 UTF-16 代码单元的输入。这些限额先于递归 Schema 校验，之后还必须满足 Schema 集合限额和 §6.6 逻辑限额。

输入是普通 JSON 数据，不是可执行对象。适配器应在解析前限制原始请求字节，并必须拒绝重复键。本地计算不发网络请求、不调用模型、不自动获取制度，也不执行任务。

## 11. 版本管理

草案版本格式为 `MAJOR.MINOR.PATCH-draft.N`。1.0 前不兼容变化必须记录变更说明并更新向量；1.0 后：

- MAJOR 可以改变线上兼容性；
- MINOR 仅增加兼容能力，不改变既有核心含义；
- PATCH 仅修正文案或测试，不改变规范行为。

Schema 标识有独立主版本。协议升级不静默激活新 Schema 或企业制度。

本次不兼容的 1.0 前修订保留 v1 Schema 家族 URN，但要求精确协议版本 `0.3.0-draft.1` 和套件 `1.0.0-draft.2`。版本分派必须选择对应发布／提交的 Schema 资产，不得将两个不同草案的同名 URN 装入同一个校验器。旧输入必须拒绝，不能只改版本号后静默迁移。

[参考实现说明](IMPLEMENTATION.md) 列出当前支持合同与评审限制。本修订不授权公开发布、采用、认证或许可证变更。

## 12. 符合性声明格式

有效声明示例：

```text
Implementation <name/version> passed <class> for BXP-0001
protocol 0.3.0-draft.1 with BXP-CALC conformance suite 1.0.0-draft.2.
```

通过要求完整结果信封一致，而非仅结论或错误码一致；不等于“零缺陷”“已认证”“可以执行”或“BoundX 已批准”。认证必须另有获得授权的认证制度。
