# BXP-0001：BoundX 任务边界协议

## 摘要

BoundX 任务边界协议（BXP）定义一种有原文证据的任务边界中间表示，以及作用于该表示的确定性计算。核心是七个任务要素——输入 I、输出 O、动作 A、责任 P、资源 R、版本与来源 V、完成与停止 C——加上独立的禁止边界 B。

BXP 不规定自然语言编译器必须怎样推断这些要素。它规定实现怎样表达抽取结果、保留不确定性、执行类型化计算，以及怎样在不作业务裁决、不授予执行权的前提下返回发现。

## 1. 当前地位

本文件是英文规范草案的中文译本，便于评审；发生差异时以 [BXP-0001.md](BXP-0001.md) 为准。它不是 IETF RFC、已采用的行业标准、认证计划或发布授权。

任何符合性声明必须包含协议版本和测试套件版本，不能笼统宣称“符合 BXP”。

## 2. 协议范围

BXP 规范：

1. 类型化、证据绑定的 7+1 任务边界 IR；
2. 确定性结构校验；
3. 区间、类型集合、跨阶段交接、前置依赖图和命题一致性计算；
4. 彼此正交的结构、完备性和一致性结果；
5. 不裁决的发现以及扩展规则；
6. 版本化一致性测试向量。

BXP 不规范某个 NLP 模型、解析器或词库，也不执行企业授权、身份、生命周期、任务执行和验收。协议计算不能证明自然语言已经被正确理解，也不能证明任务安全、合法、有价值或已经完成。

## 3. 7+1 核心

`boundx-task/v1` 冻结以下标识及含义：

| 标识 | 名称 | 规范含义 |
|---|---|---|
| I | 输入范围 | 任务涉及的对象、数据、系统或总体。 |
| O | 交付结果 | 明示的交付物或外部可观察结果。 |
| A | 允许/要求动作 | 由主体、效果和目标表达的操作。 |
| P | 责任分工 | 负责、执行、观察和审批主体。 |
| R | 资源约束 | 数量限制、预算、容量与阈值。 |
| V | 版本与来源 | 适用版本、制度、证据来源和时间基线。 |
| C | 完成与停止 | 完成、停止和升级条件。 |
| B | 禁止边界 | 被禁止的效果、目标或组合及其守卫和例外。 |

B 独立于 R。“不得超过 120 秒”是 R 的数值上界；“不得删除生产数据库”是 B 的行为边界。

每个要素桶必须明确标为：

- `resolved`：至少存在一条有证据的确定条目；
- `unresolved`：存在候选，但无法证明唯一解释；
- `absent`：来源或提交的投影中没有该要素。

不得用默认值、行业刻板映射或模型置信度把后两者静默改成 `resolved`。

## 4. 原文证据

每个确定或待消歧条目都必须包含原文 Span：精确引文 `quote`，以及按 Unicode 码点计数、左闭右开的 `start` 与 `end`。`source.text[start:end]` 必须等于 `quote`，否则 IR 无效。

证据只证明“提交的解释来自哪里”，不证明该解释唯一或正确。归一化不得覆盖原始引文，并应记录语义包及规则或模型版本。

## 5. 三个独立结果轴

协议结果不能被压成一个“通过/阻断”按钮，必须分别表达：

- `validation`：`valid | invalid`；
- `completeness`：`complete | incomplete | unresolved`；
- `consistency`：`consistent | inconsistent | undetermined`。

所有结果必须保持：

```json
{
  "business_decision": null,
  "execution_authorization": null
}
```

## 6. 数学计算

结果必须符合 `schemas/boundx-result-v1.schema.json`，并使用 `schema: boundx-result/v1`。`source_digest` 是 `source.text` 精确 UTF-8 字节的 SHA-256 小写十六进制摘要；`source_digest_algorithm` 固定为 `sha-256:utf8`。各计算集合必须使用结果 Schema 中定义的类型化对象。

### 6.1 完备性

\[
Deficit = Required(profile) \setminus Resolved(task)
\]

差集为空只证明提交的 IR 覆盖了 Profile 要求的字段，不证明自然语言抽取正确。

### 6.2 区间

只有 `(subject, dimension, unit)` 完全一致的区间才能求交。下界取最大值，上界取最小值；下界大于上界，或两者相等而至少一端为开区间时，交集为空。不同量纲和未确认的单位换算必须保持分离。

### 6.3 类型集合

请求目标和禁止目标必须处于相同对象域、动作效果、主体范围及守卫上下文，才能计算交集。交集非空是确定性冲突发现，不自动构成拒绝执行的决定。效果或对象域同一性不明时必须返回 `undetermined`。

### 6.4 跨阶段交接

交接计算必须声明生产阶段、消费阶段与制品类型。生产阶段明示产物与明示外部输入的并集构成可用供给：

\[
Available = DeclaredOutputs \cup ExternalInputs
\]

消费阶段的输入缺口为：

\[
Missing = RequiredInputs \setminus Available
\]

`Missing` 非空只证明提交的任务包存在供给差集，不证明制品在系统外绝对不存在。制品同一性未解决时必须返回 `undetermined`，不得仅凭文件名相似自动认定同一。

### 6.5 前置依赖图

只有明确标为 `prerequisite` 的边参与无环计算。参考关系、信息流和有界迭代不能被自动改写成强制前置边。发现有向环只能证明提交的强制前置关系没有拓扑顺序，不能证明线上已经发生死锁。

### 6.6 命题一致性

逻辑约束采用无量词布尔表达式，必须声明变量、假设和状态切片。`unsatisfiable` 只证明给定编码在给定假设下无解；`satisfiable` 不证明安全、授权、合法或现实可行。没有证据或 Profile 规则时，不得把不同名称的主体、目标或效果合并为同一变量。

## 7. 扩展规则

I/O/A/P/R/V/C+B 的含义在 v1 中不得重定义。新增字段必须进入 `extensions`，使用反向域名命名空间，例如 `com.example.risk-score`。

Profile 可以收紧证据、类型和必填规则，注册行业词汇和身份规则，但不得降低证据完整性、消除未知、授予执行权或重定义核心语义。所谓“第九要素”可以作为扩展存在；是否兼容由行为合同决定，而不是由“7+1、8+1”的宣传数字决定。

## 8. 符合性等级

| 等级 | 要求 |
|---|---|
| `BXP-IR` | 能读取并校验规范任务与结果 Schema。 |
| `BXP-CALC` | 完整通过指定版本 BXP-CALC 套件中的全部冻结向量。 |
| `BXP-EXTRACT` | 输出证据绑定候选并保留 unresolved/absent；单独评测。 |
| `BXP-RELAY` | 转发时保留未知命名空间扩展和核心字段。 |

自然语言抽取基准属于信息性评测，不能与确定性计算的一致性测试混为一套。历史自然语言案例只能以 `calculation-pattern-only` 方式派生计算模式向量；该派生不得宣称是原文的语义翻译或抽取金标。

## 9. 安全、版本和声明边界

实现必须限制文本长度、集合大小、表达式深度和布尔变量数，拒绝非有限数值、无效证据和未知逻辑算子。未经独立授权，不得把原文或租户语义包发送到外部模型或服务。

有效声明必须说明实现版本、BXP-0001 `0.2.0-draft.1`、符合性等级和 BXP-CALC 套件 `1.0.0-draft.1`。通过测试要求完整结果信封逐项一致，不只是结论或错误码相同；它不等于“零缺陷”“获得认证”“可以执行”或“BoundX 已批准”。
