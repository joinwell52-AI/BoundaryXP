# BXP-0001: Boundary Xplain Protocol

## Abstract

The Boundary Xplain Protocol (BXP) standardizes the expression, formalization, deterministic evaluation, identity and release admission of task boundaries.

BXP does **not** treat 7+1 as the protocol endpoint. The 7+1 structure is the standard semantic intermediate representation that carries recognized task semantics into a formal boundary model. The protocol endpoint is a deterministic **Boundary Result**: a machine-readable, referenceable, exchangeable, replayable and freezable representation of the task boundary.

For any host that publishes a task into a formal planning or execution lifecycle, BXP is a **mandatory admission contract**, not an optional advisory check. Draft tasks MAY remain incomplete and MAY enter analysis and revision. A formal task MUST NOT be released downstream unless the BXP admission conditions defined by this protocol are satisfied.

The normative processing chain is:

\[
\text{Task Semantics}
\rightarrow
IR_{7+1}
\rightarrow
\mathcal{M}(IR)
\rightarrow
\mathcal{B}
\rightarrow
Admission
\]

where:

- `Task Semantics` is the set of meanings already recognized from task source material;
- \(IR_{7+1}\) is the BXP semantic carrier;
- \(\mathcal{M}(IR)\) is the formal boundary model;
- \(\mathcal{B}\) is the deterministic Boundary Result;
- `Admission` is the host-enforced decision whether this exact task version may enter the formal downstream lifecycle.

BXP does not prescribe whether semantic recognition is produced by HanLP, spaCy, another NLP system, rules, a language model or a human reviewer. Those are producer concerns. BXP standardizes what must be represented, how uncertainty is preserved, how formal constraints are evaluated, how the final boundary is identified, and how release admission is enforced.

## 1. Status and conformance language

This document is a repository draft. It is not an IETF RFC, an adopted industry standard, a certification program or a publication authorization.

The key words MUST, MUST NOT, REQUIRED, SHOULD, SHOULD NOT, MAY and OPTIONAL are normative requirements of this draft.

This `0.4.0-draft.1` revision redefines the protocol around the Boundary Result and mandatory release admission. Matching wire schemas, conformance vectors and reference implementation changes are not yet issued. Therefore no implementation may claim conformance to `0.4.0-draft.1` until those assets are versioned and published in this repository.

## 2. Protocol purpose and mathematical definition

BXP exists to convert recognized task semantics into a deterministic boundary that can be verified, frozen, exchanged and reused without repeatedly reinterpreting the original natural language.

Let a recognized task-semantics object be denoted by \(S\). BXP defines:

\[
S
\xrightarrow{Normalize}
IR_{7+1}
\xrightarrow{Formalize}
\mathcal{M}
\xrightarrow{Evaluate}
\mathcal{B}
\]

The protocol goal is therefore not merely structural extraction. It is the production of \(\mathcal{B}\), a formal boundary result that another system can reference, compare and validate.

### 2.1 Boundary as a constraint-defined solution space

Let \(\mathcal{X}_{\Sigma}\) be the universe of candidate plans, states or downstream realizations within the declared scope \(\Sigma\). A formal boundary model defines a validity predicate:

\[
\chi_{\mathcal{M}}(x)=
Q(x)
\land \neg F(x)
\land K(x)
\land \Phi(x)
\]

where \(Q\) denotes required outcomes and obligations, \(F\) forbidden states or effects, \(K\) completion/stopping requirements, and \(\Phi\) all other formal constraints.

The admissible solution space is:

\[
\Omega_{\mathcal{B}}
=
\{x\in\mathcal{X}_{\Sigma}\mid \chi_{\mathcal{M}}(x)=true\}
\]

The Boundary Result does not need to enumerate \(\Omega_{\mathcal{B}}\). It MUST contain enough canonical information to reconstruct or verify the predicates that define it.

If:

\[
\Omega_{\mathcal{B}}=\varnothing
\]

then the formal requirements are inconsistent under the declared model.

If:

\[
\Omega_{\mathcal{B}}\neq\varnothing
\]

and all boundary-relevant identities and semantics are determined, the task may have a determined boundary.

### 2.2 Boundary-relevant interpretation uniqueness

Let \(\mathfrak{I}(S)\) be the set of admissible, source-backed semantic interpretations of the recognized task semantics. Let:

\[
\mathfrak{B}(S,O_v)
=
\{Evaluate(\mathcal{M}(I),O_v)\mid I\in\mathfrak{I}(S)\}
\]

and let \(CanonBoundary(\cdot)\) remove non-boundary presentation differences while preserving all normative boundary semantics.

The boundary is unique only if:

\[
\left|
\{CanonBoundary(b)\mid b\in\mathfrak{B}(S,O_v)\}
\right|=1
\]

If two admissible interpretations produce materially different boundary results, the task is `underdetermined` until authoritative clarification removes the ambiguity.

This criterion is stronger and more precise than merely checking whether every 7+1 bucket is populated.

### 2.3 Separation of responsibilities

The protocol MUST preserve a strict distinction between:

1. semantic recognition;
2. semantic representation;
3. formalization;
4. deterministic boundary evaluation;
5. release admission;
6. business or execution decisions.

BXP standardizes stages 2–5. Stage 1 may be implemented by different producers. Stage 6 remains outside BXP authority.

## 3. Layer 1 — 7+1 semantic carrier

The 7+1 semantic intermediate representation is:

\[
IR_{7+1}=(I,O,A,P,R,V,C,B)
\]

with the following fixed meanings:

| ID | Name | Normative meaning |
|---|---|---|
| I | Input | Objects, data, systems, populations or other task inputs and in-scope subjects. |
| O | Output | Declared deliverables or externally observable results. |
| A | Actions | Required, permitted or otherwise task-relevant operations, preserving actor, effect, target and modality where known. |
| P | Participants | Humans, Agents, systems and services participating in execution, approval, observation, review, receipt or collaboration. |
| R | Resources | Quantitative limits, budgets, capacities, deadlines, durations and thresholds. |
| V | Version / Provenance | Controlling versions, policies, evidence sources and temporal baselines. |
| C | Completion | Completion, stop, acceptance and escalation conditions. |
| B | Forbidden Boundary | Prohibited effects, targets, actions or combinations, including their guards and exceptions. |

The 7+1 structure is a semantic coordinate system, not the final mathematical boundary:

\[
IR_{7+1}\neq\mathcal{B}
\]

A conforming implementation MUST NOT describe a populated 7+1 structure by itself as the final Boundary Result.

Each element MUST preserve explicit uncertainty using at least `resolved`, `unresolved` and `absent`. No producer confidence score, default domain assumption or model preference may silently convert an unresolved interpretation into a resolved one.

## 4. Evidence and semantic identity

Every resolved or unresolved semantic claim MUST remain traceable to source evidence.

Evidence establishes where a submitted semantic claim came from. Evidence alone does not prove that the interpretation is complete, unique or correct.

A producer MUST preserve ambiguity if multiple materially different interpretations remain possible. If different interpretations would produce different formal models or different Boundary Results, the ambiguity is boundary-relevant and MUST NOT be collapsed by guesswork.

For interpretations \(I_i\) and \(I_j\):

\[
CanonBoundary(\mathcal{B}(I_i))
\neq
CanonBoundary(\mathcal{B}(I_j))
\Rightarrow
State=underdetermined
\]

until new evidence, clarification or an authoritative choice resolves the difference.

## 5. Layer 2 — Formal Boundary Model

The semantic IR MUST be transformed into a formal model before deterministic boundary evaluation.

BXP defines the abstract model:

\[
\mathcal{M}(IR)=
(E,\Sigma,Q,F,K,\mathcal{R},D,\Phi)
\]

where:

- \(E\): identified entities and artifacts;
- \(\Sigma\): explicit scopes and state slices;
- \(Q\): required outcomes and obligations;
- \(F\): forbidden actions, targets, effects or state combinations;
- \(K\): completion and stopping conditions;
- \(\mathcal{R}\): participant, role and relation facts;
- \(D\): dependency, handoff, provenance and version relations;
- \(\Phi\): formal constraints such as numeric, set, logical, temporal or ordering predicates.

This tuple is an abstract protocol model. A wire representation MAY encode it using multiple typed collections rather than one literal tuple.

Examples:

\[
\text{“duration must not exceed 10 minutes”}
\Rightarrow
 duration\le600s
\]

\[
\text{“without ADMIN approval, publishing is forbidden”}
\Rightarrow
\neg approved_{ADMIN}\Rightarrow\neg publish
\]

\[
\text{“the production database must not be modified”}
\Rightarrow
ModifiedTargets\cap ProductionDatabase=\varnothing
\]

Formalization MUST NOT invent facts absent from the semantic IR. If identity, unit, scope, relation or applicability is not determined, the formal model MUST preserve that lack of determination instead of manufacturing a computable value.

## 6. Layer 3 — Boundary evaluation

Boundary evaluation applies a versioned operator profile \(O_v\) to a formal model:

\[
\mathcal{B}=Evaluate(\mathcal{M},O_v)
\]

For identical \(\mathcal{M}\) and identical \(O_v\), the evaluator MUST produce the same \(\mathcal{B}\):

\[
\mathcal{M}_1=\mathcal{M}_2\land O_{v1}=O_{v2}
\Rightarrow
Evaluate(\mathcal{M}_1,O_{v1})=Evaluate(\mathcal{M}_2,O_{v2})
\]

Evaluation MUST NOT depend on random sampling, wall-clock time, model temperature, network responses or other undeclared external state.

### 6.1 Operator profiles are mechanisms, not the protocol core

BXP may define or register deterministic operator families including, but not limited to interval algebra, typed-set operations, handoff/data-flow analysis, dependency graphs, propositional logic, temporal constraints, ordering, cardinality, identity/equivalence, reachability, resources, and version/provenance checks.

The availability of any particular operator family does not define BXP itself. Operator families are versioned mechanisms used to evaluate the formal boundary model.

An operator family MUST have deterministic semantics, bounded input rules, explicit unresolved behavior and machine-testable output.

## 7. Layer 4 — Boundary Result

The Boundary Result is the final protocol data object.

A Boundary Result MUST answer:

1. **Is the task boundary determined?**
2. **If determined, what is that boundary?**

The abstract result is:

\[
\mathcal{B}=
(State,Required,Forbidden,Limits,Completion,Relations,Dependencies,Provenance,Findings)
\]

A wire schema MAY organize these components differently, but it MUST preserve their semantics and deterministic identity.

### 7.1 Boundary state

A Boundary Result MUST expose one of the following states or an equivalent versioned representation:

- `determined` — boundary-relevant semantics and identities required by the active profile are resolved, the formal model is valid, the canonical boundary is unique, and required evaluation results are deterministic and non-conflicting;
- `underdetermined` — unresolved semantics, identity, scope, unit, applicability or other uncertainty can materially change the Boundary Result;
- `inconsistent` — the model is sufficiently determined to prove that submitted requirements cannot all hold together;
- `invalid` — submitted protocol data is structurally or semantically invalid and no valid boundary may be produced.

A result MUST NOT use `determined` merely because calculation code finished.

An abstract determination condition is:

\[
Determined(\mathcal{B})=
Valid
\land RequiredResolved
\land IdentityResolved
\land ScopeResolved
\land UniqueCanonicalBoundary
\land Consistent
\]

where:

\[
UniqueCanonicalBoundary
\iff
\left|\{CanonBoundary(b)\mid b\in\mathfrak{B}(S,O_v)\}\right|=1
\]

Profiles MAY refine this condition but MUST NOT weaken uncertainty preservation.

### 7.2 Accuracy

BXP accuracy means exact evaluation of the supplied formal model and the absence of false certainty.

If semantics remain ambiguous in a way that can change the result:

\[
Ambiguous\not\Rightarrow ChooseMostLikely
\]

Instead:

\[
Ambiguous\Rightarrow underdetermined
\]

BXP does not claim that a parser or NLP producer always understands natural language correctly. Extraction quality requires separate evidence and conformance criteria. BXP does require that the evaluator never disguise known uncertainty as a determined boundary.

## 8. Mandatory task admission contract

BXP is the mandatory admission contract for formal task release.

A host MAY allow an incomplete or underdetermined draft to exist in drafting, analysis, clarification and revision states. A host MUST NOT publish that task into the formal downstream planning or execution lifecycle until admission succeeds.

Define the release admission predicate:

\[
Admit(T_v)=
ProtocolValid(T_v)
\land BoundaryDetermined(T_v)
\land ReleaseConditions(T_v)
\land VersionBound(T_v)
\]

Only when:

\[
Admit(T_v)=true
\]

MAY the host publish the formal task downstream.

If:

\[
Admit(T_v)=false
\]

or admission cannot be computed, the host MUST fail closed and MUST NOT release the task.

### 8.1 Admission is not “7+1 filled”

The following implication is explicitly invalid:

\[
AllBucketsNonEmpty\not\Rightarrow Admit(T_v)
\]

Likewise:

\[
Completeness=complete\not\Rightarrow Admit(T_v)
\]

Admission requires the full protocol predicate, including formal validity, boundary determination, consistency, release-profile conditions and exact version binding.

### 8.2 Drafts and formal tasks

Draft status is not a failure. Drafts MAY be incomplete, inconsistent or underdetermined while they are being analyzed or revised.

Formal release is different. A task marked or treated as formally released MUST satisfy BXP admission. A host MUST NOT use UI warnings, banners, optional buttons, acknowledgements or model suggestions as a substitute for enforcement.

### 8.3 Changes invalidate prior admission

Let \(D_S(T_v)\) be the exact source identity of the admitted task version. If ADMIN or another authoritative source modifies the task so that:

\[
D_S(T_{v+1})\neq D_S(T_v)
\]

then:

\[
Admission(T_v)\not\Rightarrow Admission(T_{v+1})
\]

and the prior admission MUST be treated as stale even if the new task later happens to compute to an equivalent boundary. The modified task MUST be revalidated, reformalized where necessary, reevaluated and readmitted.

### 8.4 Release binding

A formal release SHOULD be bound by a canonical admission identity such as:

\[
D_A=
Hash(
ProtocolVersion,
Profile,
D_S,
D_{IR},
D_M,
O_v,
D_B
)
\]

where \(D_A\) identifies the exact admitted task/boundary combination.

The host MUST reject a release when the currently recomputed binding differs from the stored admission binding:

\[
D_A^{current}\neq D_A^{admitted}
\Rightarrow
Release=blocked
\]

### 8.5 Host enforcement

The producer proposes semantic candidates. BXP validates, formalizes and computes. The host MUST enforce the resulting admission state.

A model output, UI suggestion, button label, warning, cached result or operator statement MUST NOT independently bypass a failed, stale or mismatched BXP admission.

### 8.6 Admission is not execution authorization

BXP admission means only that a task is mathematically and structurally eligible to enter the formal downstream lifecycle under the declared BXP profile.

\[
Admission\neq ExecutionAuthorization
\]

Business approval, actor authorization, credentials, runtime safety checks and execution permissions remain the responsibility of their respective systems.

## 9. Referenceability, exchangeability and freezing

Boundary Results are stable data objects, not prose advice.

A conforming result model SHOULD bind at least:

\[
D_S=Hash(Source)
\]

\[
D_{IR}=Hash(IR_{7+1}+FormalizationInputs)
\]

\[
D_M=Hash(Canonical(\mathcal{M}))
\]

\[
D_B=Hash(Canonical(\mathcal{B}))
\]

Any change that changes the deterministic Boundary Result MUST change \(D_B\).

A stable reference MAY be modeled as:

\[
Ref_{\mathcal{B}}=(ProtocolVersion,Profile,O_v,D_B)
\]

A Boundary Result is **referenceable** when a downstream system can bind to this identity without reinterpreting natural language.

It is **exchangeable** when another implementation can validate the schema, protocol version, operator profile and digests without requiring the same NLP engine or producer.

It is **freezable** when exact inputs, operator profile and canonical result identity are pinned so later changes cannot silently mutate the referenced boundary.

It is **replayable** when an independent conforming evaluator can recompute:

\[
Evaluate(\mathcal{M},O_v)=\mathcal{B}
\]

and obtain the same canonical result identity.

## 10. Producer independence

BXP does not standardize a particular semantic recognition engine.

A producer MAY use HanLP, spaCy, another NLP framework, deterministic rules, statistical models, neural models, an LLM, human annotation or a combination of these.

Producer choice MUST NOT change the meanings of I/O/A/P/R/V/C/B or the formal semantics of the Boundary Result.

For semantically equivalent producer outputs:

\[
IR_a\equiv IR_b
\land
\mathcal{M}(IR_a)=\mathcal{M}(IR_b)
\Rightarrow
\mathcal{B}_a=\mathcal{B}_b
\]

under the same operator profile.

## 11. Downstream conformance

An admitted Boundary Result is designed to serve as a reference baseline for downstream plans, decompositions and implementations.

For a downstream object \(X\):

\[
Conform(X,\mathcal{B})
\iff
X\in\Omega_{\mathcal{B}}
\]

or equivalently:

\[
X\models\chi_{\mathcal{M}}
\]

Typical diagnostic decompositions include:

\[
Missing=Required_{\mathcal{B}}\setminus Covered_X
\]

\[
Violation=Actions_X\cap Forbidden_{\mathcal{B}}
\]

\[
ConstraintViolation=
\{\phi\in\Phi_{\mathcal{B}}\mid X\not\models\phi\}
\]

BXP does not require the downstream consumer to be a PM, Agent, workflow engine or human team. It standardizes the boundary data that such consumers may reference.

## 12. Current operator families

The existing BXP implementation lineage includes several deterministic operator families. They remain useful mechanisms, but they are not the definition of BXP.

### 12.1 Profile completeness

\[
Deficit=Required(profile)\setminus Resolved(IR)
\]

### 12.2 Interval intersection

\[
L=\max_i L_i,\qquad U=\min_i U_i
\]

### 12.3 Typed-set overlap

\[
Overlap=RequestedTargets\cap ForbiddenTargets
\]

### 12.4 Handoff deficit

\[
Available=DeclaredOutputs\cup ExternalInputs
\]

\[
Missing=RequiredInputs\setminus Available
\]

### 12.5 Dependency consistency

A mandatory prerequisite relation is inconsistent when its directed graph contains a cycle.

### 12.6 Propositional consistency

For a resolved scope, all submitted formulas and assumptions are conjoined. The result is satisfiable when at least one valuation exists and unsatisfiable otherwise.

These operator families MAY evolve independently under versioned operator profiles, provided protocol determinism and result semantics remain intact.

## 13. Authority boundary

A Boundary Result describes computed task-boundary facts. It does not itself make a business decision, grant permission, authorize execution, prove legality, prove safety or prove task completion.

Every conforming wire result that exposes authority fields MUST preserve the equivalent of:

```json
{
  "business_decision": null,
  "execution_authorization": null
}
```

No BXP conformance class may redefine a determined boundary or successful admission as execution authorization.

## 14. Versioning and migration

Draft versions use `MAJOR.MINOR.PATCH-draft.N`.

`0.4.0-draft.1` changes the conceptual center of BXP from “7+1 plus a fixed set of calculations” to:

\[
\boxed{
TaskSemantics
\rightarrow
IR_{7+1}
\rightarrow
FormalBoundaryModel
\rightarrow
BoundaryResult
\rightarrow
Admission
}
\]

This draft intentionally does not claim that the current `boundx-task/v1`, `boundx-result/v1` schemas, existing frozen vectors or current product host already implement all new Boundary Result and mandatory admission requirements. A later implementation task must version the affected schemas, operator profile, conformance suite, release record and host gate before `0.4.0-draft.1` can be claimed as implemented.

Existing `0.3.0-draft.2` wire behavior remains historical implementation evidence and MUST NOT be relabeled as `0.4.0-draft.1` conformance.

## 15. Core definition

The stable core of BXP is not 7+1 by itself and is not any particular calculation algorithm.

The stable core is:

\[
\boxed{
IR_{7+1}
\rightarrow
\mathcal{M}(IR)
\rightarrow
\mathcal{B}
\rightarrow
Admission
}
\]

BXP uses a standard semantic carrier to construct a formal task-boundary model, deterministically produces a Boundary Result, and requires that formal task release be admitted against that exact result.

7+1 exists to serve formalization.

Formalization exists to serve deterministic evaluation.

Deterministic evaluation exists to produce the Boundary Result.

The Boundary Result exists to provide a precise, referenceable and exchangeable boundary baseline.

Admission exists to ensure that no formal task enters the downstream lifecycle without satisfying that boundary contract.
