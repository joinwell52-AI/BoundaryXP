# BXP-0001: BoundX Task Boundary Protocol

## Abstract

The BoundX Task Boundary Protocol (BXP) defines an evidence-linked intermediate representation for task boundaries and deterministic calculations over that representation. Its core is seven task elements — Input, Output, Actions, Participants, Resources, Version/Provenance and Completion — plus an independent Forbidden Boundary element.

BXP does not define how a natural-language compiler must infer those elements. It defines how an implementation represents extracted claims, preserves uncertainty, performs typed calculations and reports findings without making a business decision or granting execution authority.

## 1. Status and conformance language

This document is a repository draft. It is not an IETF RFC, an adopted industry standard, a certification program or a publication authorization.

The key words MUST, MUST NOT, REQUIRED, SHOULD, SHOULD NOT, MAY and OPTIONAL are to be interpreted as normative requirements of this BXP draft.

An implementation MUST state the exact protocol version, conformance class, and applicable test-suite version it targets. “BXP conformant” without a version is not a valid conformance claim.

## 2. Scope

BXP standardizes:

1. a typed, evidence-linked 7+1 task-boundary IR;
2. deterministic structural validation;
3. interval, typed-set, cross-stage handoff, prerequisite-graph and propositional-consistency calculations;
4. orthogonal validation, completeness and consistency outcomes;
5. non-adjudicative findings and extension rules;
6. versioned conformance vectors.

BXP does not standardize:

- a particular NLP model, parser, grammar or domain dictionary;
- enterprise authorization, identity, workflow or lifecycle systems;
- task execution, acceptance, publication or recovery;
- a proof that the source text was interpreted correctly;
- a proof that a task is safe, lawful, useful or completed.

## 3. Core 7+1 model

The core element identifiers are frozen for the `boundx-task/v1` major version:

| ID | Name | Normative meaning |
|---|---|---|
| I | Input | Objects, data, systems or populations in scope. |
| O | Output | Declared deliverables or externally observable results. |
| A | Actions | Permitted or required operations represented by actor, effect and target. |
| P | Participants | Responsibility holders and role assignments: humans, Agents, systems and services that execute, approve, observe, receive, review or collaborate. Recording approval relationships never grants execution authority. |
| R | Resources | Quantitative limits, budgets, capacities and thresholds. |
| V | Version / Provenance | Controlling versions, policies, evidence sources and temporal baselines. |
| C | Completion | Completion, stop and escalation conditions. |
| B | Forbidden Boundary | Prohibited effects, targets or combinations, including their guards and exceptions. |

B is independent from R. A negative numeric comparator such as “must not exceed 120 seconds” is an R upper bound; a prohibition on an effect such as “must not delete the production database” is B.

Each element bucket has one of three explicit statuses:

- `resolved`: at least one source-backed entry is present;
- `unresolved`: one or more candidates exist but the implementation cannot prove a unique interpretation;
- `absent`: the source or submitted projection contains no entry for the element.

An implementation MUST NOT convert `unresolved` or `absent` into `resolved` by default values, domain stereotypes or model confidence alone.

## 4. Evidence contract

Every resolved or unresolved entry MUST contain at least one evidence span. A span consists of:

- the exact `quote` from the selected source text;
- inclusive `start` and exclusive `end` offsets measured in Unicode code points;
- an optional `source_id`; omission means the primary source, whose reserved ID is `task`.

The bounds MUST satisfy `0 <= start < end <= codePointLength(text)`, and the substring selected by `[start, end)` MUST equal `quote`. Out-of-range offsets MUST NOT be clipped. Unpaired surrogates MUST be rejected; no Unicode normalization, newline conversion, trimming or translation may precede evidence comparison or hashing. Chinese, English and mixed-language sources use the same rules; UTF-16 code units and UTF-8 byte offsets are not code-point offsets.

Optional `sources` declares up to 16 secondary documents with unique `id`, `kind` (`policy`, `clarification` or `reference`), nonempty `version`, `language`, exact `text`, and `digest` (lowercase SHA-256 of that text's UTF-8 bytes). IDs MUST NOT redefine `task`. Unknown source references and digest mismatches invalidate the IR. Sources are supplied locally; an evaluator MUST NOT fetch a policy URL or silently select a newer version. A source digest establishes content identity, not authenticity, policy applicability or authority. Evidence proves where a submitted claim came from; it does not prove that the claim is the only or correct interpretation.

Normalization MUST preserve the original quote and SHOULD record the semantic-pack identifier and rule or model version that produced the normalized value.

## 5. Canonical task envelope

A task envelope MUST conform to `schemas/boundx-task-v1.schema.json` and contains:

```json
{
  "schema": "boundx-task/v1",
  "protocol_version": "0.3.0-draft.2",
  "task_id": "example-001",
  "source": { "language": "zh-CN", "text": "..." },
  "profile": {
    "id": "org.boundx.core-7plus1",
    "required_elements": ["I", "O", "A", "P", "R", "V", "C", "B"]
  },
  "elements": {
    "I": { "status": "absent", "entries": [] },
    "O": { "status": "absent", "entries": [] },
    "A": { "status": "absent", "entries": [] },
    "P": { "status": "absent", "entries": [] },
    "R": { "status": "absent", "entries": [] },
    "V": { "status": "absent", "entries": [] },
    "C": { "status": "absent", "entries": [] },
    "B": { "status": "absent", "entries": [] }
  },
  "constraints": {
    "intervals": [],
    "target_sets": [],
    "handoffs": [],
    "dependencies": [],
    "logic": []
  },
  "extensions": {}
}
```

This is a structurally valid but incomplete envelope, not a resolved task. A `resolved` bucket with no entries is invalid. Schema validation MUST be complete, without coercion, default insertion or property removal, and MUST precede semantic validation and calculation. Any invalidity stops all calculations. Element entry IDs MUST be unique across all eight buckets; constraint IDs, where present, MUST be unique within their collection. `normalized` is optional opaque producer metadata, not executable logic; calculations use only the typed `constraints` collections.

### 5.1 Explicit calculation scopes

Optional `scopes` declares up to 128 distinct scopes with `id`, source-backed `description`, `identity_status` (`resolved` or `unresolved`) and `evidence`. The reserved scope `task` is implicit and cannot be redefined. Every typed constraint MAY specify `scope_id`; omission explicitly means the common task-level scope, not an inferred stage, actor identity or condition. Every calculation result MUST include its `scope_id`.

An undeclared scope reference is invalid. All calculations under an unresolved scope MUST be skipped with `BXP.SCOPE.UNRESOLVED`; unrelated resolved scopes still calculate. Scopes are separate submitted state slices, not an executable condition language. There is no implicit inheritance from `task` into other scopes, cross-scope satisfiability, stage scheduling, or policy precedence. A producer MUST explicitly project applicable global constraints into each relevant scope with evidence, and MUST preserve unresolved applicability rather than claiming an exemption. The evaluator cannot prove that this projection is complete or correct.

## 6. Deterministic calculations

### 6.1 Profile completeness

For a selected profile, let `Required(profile)` be its required element identifiers and let `Resolved(task)` contain only buckets whose status is `resolved` and whose entries are non-empty.

\[
Deficit = Required(profile) \setminus Resolved(task)
\]

`Deficit = ∅` proves only profile coverage of the submitted IR. It does not prove extraction correctness or semantic equivalence to the source.

### 6.2 Interval algebra

An interval is typed by `(scope_id, subject, dimension, unit, domain)`. `domain` is `real` (the default mathematical domain) or `integer`. Mixing domains under the same first four key components is invalid. Only intervals with identical normalized keys may be intersected. Bounds retain open or closed endpoints. Producers MUST NOT submit a resolved key when identity or conversion remains unresolved; they must retain unresolved evidence in the relevant element instead.

An input bound value MUST be either a JSON integer in `[-9007199254740991, 9007199254740991]` or a decimal string matching `^-?(?:0|[1-9][0-9]*)(?:\.[0-9]+)?$`, at most 256 characters. All fractional and larger values MUST be strings, without exponent notation, grouping, units or a leading plus. An implementation MUST compare exact decimal values, without binary floating-point rounding, epsilon or implicit unit conversion. Infinity is expressed only by a null bound; both bounds cannot be null.

Result bounds MUST use canonical decimal strings: remove redundant fractional trailing zeros and a trailing decimal point, and render all zero values as `0`. Integer-domain normalization uses `ceil(lower)` / `floor(upper)` for inclusive bounds and `floor(lower)+1` / `ceil(upper)-1` for exclusive bounds; its resulting endpoints are inclusive. Calculated strings allow 257 characters for a carry at the input limit. These defaults describe the submitted mathematical model, not missing task facts.

\[
L = \max_i L_i, \qquad U = \min_i U_i
\]

The intersection is empty when `L > U`, or when `L = U` and at least one selected endpoint is open. Different dimensions or unresolved unit conversions MUST remain separate; they MUST NOT be reported as compatible merely because each local interval is non-empty.

### 6.3 Typed set overlap

A target-set calculation is valid only when the requested and forbidden sets share the same declared universe, action effect, actor scope and guard context.

\[
Overlap = RequestedTargets \cap ForbiddenTargets
\]

A non-empty overlap is a consistency finding. It is not itself an execution denial or an authorization decision. If effect identity or universe identity is unresolved, the calculation result is `undetermined`.

### 6.4 Cross-stage handoff

A handoff calculation is typed by producer stage, consumer stage and artifact type. Let `DeclaredOutputs` be the producer's submitted outputs, `ExternalInputs` be explicitly declared external supplies and `RequiredInputs` be the consumer's submitted requirements.

\[
Available = DeclaredOutputs \cup ExternalInputs
\]

\[
Missing = RequiredInputs \setminus Available
\]

`Missing != empty` is a submitted data-flow deficit. It does not prove that an artifact does not exist outside the envelope. If artifact identity is unresolved, the result MUST be `undetermined`; an implementation MUST NOT equate artifacts by filename similarity alone.

### 6.5 Prerequisite graph

Only edges explicitly typed `prerequisite` participate in the mandatory acyclicity calculation, separately per scope. Reference, information-flow and bounded-iteration edges do not become prerequisites by implication.

The prerequisite graph is inconsistent when it contains a directed cycle. A cycle finding means the submitted mandatory dependency relation has no topological order; it does not prove an observed runtime deadlock.

### 6.6 Propositional consistency

The `logic` collection uses a quantifier-free Boolean expression AST. Each item MUST declare its local variables; every variable reference in its formula and optional assumptions MUST be locally declared. Omitted assumptions mean Boolean `true`, not an assumed business permission. Within one resolved scope, all member formulas AND all submitted assumptions MUST be conjoined into one calculation. Identically named variables share one truth value only within that scope. Different scopes have independent valuations. Splitting contradictory formulas into separate items MUST NOT hide their conjunction's contradiction.

Each scope has at most 12 distinct variables; each AST has depth at most 16 (root depth zero), and all formulas plus assumptions together have at most 4096 AST nodes. Supported operators are `var`, `not`, `all`, `any` and `implies`; `all` and `any` require 1–64 operands, and `implies` exactly two. Boolean literals are allowed. Exceeding a limit is invalid, not satisfiable or silently truncated.

The result is `satisfiable` or `unsatisfiable` for a resolved scope; unresolved scopes are skipped with an unresolved finding. Each logic result uses `id = scope_id` and includes sorted `constraint_ids`. Unsatisfiable results have `witness: null`; satisfiable results carry the first assignment in sorted-variable lexicographic order with `false` before `true`.

`unsatisfiable` proves only that no assignment satisfies the submitted formula under the submitted normalization and state slice. `satisfiable` does not prove safety, authority, legality or real-world feasibility.

An implementation MUST NOT normalize differently named actors, targets or effects to one Boolean variable without a source-backed identity assertion or an explicit profile rule.

## 7. Result envelope and authority boundary

A result MUST conform to `schemas/boundx-result-v1.schema.json` and use `schema: boundx-result/v1`. Its principal axes are independent:

- `validation`: `valid` or `invalid`;
- `completeness`: `complete`, `incomplete`, `unresolved` or `undetermined`;
- `consistency`: `consistent`, `inconsistent` or `undetermined`.

Every result MUST contain:

```json
{
  "business_decision": null,
  "execution_authorization": null
}
```

`source_digest` MUST be lowercase SHA-256 over the exact UTF-8 bytes of `source.text`, and `source_digest_algorithm` MUST be `sha-256:utf8`. `input_digest` MUST additionally bind the whole submitted JSON value, including profile, scopes, sources, constraints and extensions, using the canonical serialization in §7.1. It is a content digest, not a signature or proof of policy adoption. Calculation collections MUST use the typed result objects defined by the result schema; unconstrained implementation-specific objects are not conformant.

Aggregation order is normative: invalid input gives `validation=invalid`, both other axes `undetermined`, and all calculation arrays empty. Otherwise completeness is `unresolved` if any required bucket is unresolved, else `incomplete` if any required bucket is absent, else `complete`. Consistency is `inconsistent` if any calculated conflict exists, else `undetermined` if any element (including optional elements), scope or calculated identity is unresolved, else `consistent`. Thus an unrelated unknown MUST NOT mask a proven conflict. `consistent` means only no conflict found in the submitted, resolved calculations; it is not proof of extraction coverage, cross-unit compatibility or real-world feasibility.

### 7.1 Deterministic serialization and diagnostics

Input digests MUST use [RFC 8785 JCS](https://www.rfc-editor.org/rfc/rfc8785.html), with `input_digest_algorithm: sha-256:jcs-rfc8785`. No Unicode normalization is permitted. Canonical input serialization recursively sorts object keys by UTF-16 code-unit order, preserves array order, emits no whitespace, and serializes strings, finite numbers, booleans and null using ECMAScript JSON scalar serialization (including negative zero as `0`). SHA-256 is taken over the resulting UTF-8 bytes. Object insertion order is not significant; array order is significant. Decoders MUST reject duplicate JSON keys before constructing the task object, since they cannot be recovered by a post-parse evaluator. The reference object API accepts already-decoded JSON data; it does not claim duplicate-key detection for a caller's decoder.

Schema/preflight failures return one `BXP.IR.INVALID_ENVELOPE` finding. Semantic validation returns the first invalid finding, in source order, scope order, core order I/O/A/P/R/V/C/B, then collection order intervals/target_sets/handoffs/dependencies/logic and input item order. Successful findings follow core order, unresolved scopes, then those five calculation collections. Arrays of calculations preserve input order or first occurrence of a grouping key. Evidence is deduplicated by full span equality while retaining first occurrence; aggregate finding evidence allows up to 16384 spans, while each submitted evidence list remains limited to 32. A finding's evidence is supporting context, not a minimal unsatisfiable core.

Target overlap, handoff available/missing sets and Boolean names/constraint IDs are sorted by UTF-16 code-unit order. Prerequisite graph traversal visits sorted nodes and sorted unique neighbors with depth-first visiting/done sets; each back edge emits a cycle object with `nodes` (starting node repeated) and `edge_ids` in traversal order. For parallel prerequisite edges with identical endpoints in one scope, the lexically smallest ID represents the connection; all submitted edges still count. Equal node paths are deduplicated in encounter order. These are deterministic cycle witnesses, not an enumeration of every graph cycle. Edge counts count submitted prerequisite edges, including duplicates. With no submitted dependency edges, one empty `task` graph is returned; scopes whose submitted edges are all skipped have no graph result.

Invalid results always advertise the evaluator's supported version, never echo an unsupported caller version. A bounded nonempty string `task_id` of at most 256 code points is retained, otherwise `invalid-task` is used. If the input fails JSON/Unicode/resource preflight, `input_digest` is the digest of JSON null, the task ID is `invalid-task`, and the primary source digest is that of the empty string. For other invalid inputs, the input digest binds the submitted value; an absent, non-string or overlong primary source likewise uses the empty-string digest. These diagnostic fallbacks do not assert valid task content.

Every emitted result, including errors, MUST satisfy the result Schema. Exact-suite comparison ignores JSON object key order but compares array order and all values, including stable English diagnostic messages. Chinese/English display translation MAY be layered on stable `code`, `path`, statuses and numeric results; it MUST NOT translate or overwrite evidence or change a frozen wire result. Localized displays are not new protocol versions.

No conformance level permits a BXP engine to replace a task authorizer, accountable owner, reviewer or external approval system. Findings describe computed facts, assumptions and missing information.

Numeric decoders MUST preserve bound-value precision or reject a numeric token before rounding would turn it into an apparently valid safe integer. The object evaluator cannot reconstruct a rounded caller input. Decimal-string bounds avoid this loss; the reference object API is not a raw JSON transport or a precision-preserving parser.

### 7.2 Result invariants and traceability

Result Schema MUST reject: invalid input with non-undetermined axes or nonempty calculation arrays; satisfiable logic without an object witness; unsatisfiable/undetermined logic with a non-null witness; overlap with an empty overlap array; disjoint/undetermined targets with a nonempty overlap array; deficit handoffs without missing items; satisfied/undetermined handoffs with missing items. Undetermined handoffs also have empty available arrays.

Valid results MUST include `applied_profile` (submitted ID and required elements), `resolved_elements` (all resolved buckets, including optional ones), and `deficit` (each required non-resolved bucket as `{element, status}`, status absent or unresolved). Element lists use I/O/A/P/R/V/C/B order. Applied profile IDs are caller assertions, not proof of external profile loading or compliance. Invalid results MUST use null applied_profile and empty resolved_elements/deficit. Complete implies empty deficit; incomplete implies nonempty absent-only deficit; unresolved requires at least one unresolved deficit. These fields MUST correspond to the submitted task, not merely satisfy Schema.

Interval results MUST include sorted IDs of all contributing constraints, not only tight bounds. Every submitted dependency edge MUST have an ID unique across its collection, including different scopes and non-prerequisite kinds. Cycle edge IDs MUST identify the actual same-scope prerequisite edges joining consecutive nodes; node count equals edge count plus one. Schema checks shape; CALC verification checks these cross-input relationships and mathematical truth.

## 8. Extensions and profiles

The I/O/A/P/R/V/C+B identifiers and their meanings MUST NOT be redefined within `boundx-task/v1`.

Additional fields MUST be placed under `extensions` and use a reverse-domain namespace such as `com.example.risk-score`. An implementation MAY ignore an extension it does not understand but MUST preserve it when forwarding an envelope unchanged.

A profile MAY:

- select required core elements;
- add stricter evidence or type requirements;
- register domain vocabularies and identity rules;
- require namespaced extensions.

A profile MUST NOT weaken evidence integrity, erase uncertainty, grant execution authority or redefine core semantics. A vendor may add a ninth concept as an extension and remain core-compatible; incompatibility is determined by behavior, not marketing arithmetic.

This reference evaluator enforces the submitted `required_elements` only; it does not load an arbitrary profile by ID, execute `normalized` metadata or activate semantic packs. Producers SHOULD pin external profile/pack/rule versions and content digests in a namespaced provenance extension. A namespace or source kind does not establish trust. L1 general, L2 industry and L3 enterprise remain producer layers over this one protocol; none may silently override B or turn a source policy into execution authorization. Task extensions are included in the input digest but are not copied into a newly computed result's empty `extensions`. Forwarding the same envelope is a different BXP-RELAY obligation.

## 9. Conformance classes

An implementation MUST claim one or more explicit classes:

| Class | Requirement |
|---|---|
| `BXP-IR` | Validates the exact task/result schemas and semantic invariants; names versioned positive/negative test evidence. Schema acceptance alone does not prove calculation correctness. |
| `BXP-CALC` | Passes every frozen vector in the exact named BXP-CALC suite. |
| `BXP-EXTRACT` | RESERVED / INFORMATIVE. Passing claims MUST NOT be made in this draft. |
| `BXP-RELAY` | Preserves the complete same envelope, including unknown extensions, core fields, evidence, array order and digests; claims require versioned forwarding tests. This calculator does not claim RELAY. |

Extraction gold count is zero. Activation of BXP-EXTRACT requires a versioned independent gold set, scoring and tolerance rules covering exact spans, element precision/recall/F1, status accuracy, operators/units/scopes, forbidden-vs-numeric negation, anaphora ambiguity and false-resolution rates. These are future evaluation requirements, not current quality claims.

Natural-language extraction benchmarks are informative evaluation artifacts, not normative calculation vectors. Historical scenarios may inspire structured calculation vectors only when the derivation is explicitly marked `calculation-pattern-only`; those derivatives MUST NOT be represented as semantic translations or proof of extraction quality.

## 10. Security and privacy

Implementations MUST treat source text and tenant semantic packs as potentially sensitive. They MUST NOT send data to external models or services without an independently established authorization. Logs SHOULD store digests and bounded evidence rather than unrestricted source text.

An implementation MUST bound input length, collection size, expression depth and Boolean variable count. It MUST reject non-finite numbers, invalid Unicode evidence and unsupported expression operators.

For this BXP-CALC draft, a decoded JSON task has at most 100000 value nodes, nesting depth 64 (root zero), and 2000000 UTF-8 bytes after compact ECMAScript JSON serialization. Each primary or secondary source has at most 100000 code points. The reference preflight also rejects more than 2000000 UTF-16 code units across keys and string values. These limits precede recursive Schema validation; Schema collection limits and §6.6 logic limits then apply. Inputs are plain JSON data, not executable objects. Sparse/decorated arrays, symbol keys, hidden properties and accessors MUST be rejected by the reference object API before hashing. Adapters SHOULD bound raw request bytes before parsing and MUST reject duplicate keys. The local calculation path performs no network requests, model calls, policy retrieval or task execution.

## 11. Versioning

Draft versions use `MAJOR.MINOR.PATCH-draft.N`. Before 1.0, incompatible changes are permitted only with a recorded change note and updated conformance vectors. After 1.0:

- MAJOR changes may break wire compatibility;
- MINOR changes are additive and preserve existing core meaning;
- PATCH changes repair wording or tests without changing normative behavior.

Schema identifiers carry their own major version. A protocol version bump does not silently activate a new schema or enterprise policy.

This incompatible pre-1.0 revision requires exact `protocol_version: 0.3.0-draft.2` and suite `1.0.0-draft.3`. Wire family fields remain `boundx-task/v1` and `boundx-result/v1`, but resource `$id` values are `urn:boundx:schema:task:v1:0.3.0-draft.2`, `urn:boundx:schema:result:v1:0.3.0-draft.2` and `urn:boundx:schema:calc-conformance-suite:v1:1.0.0-draft.3`. Every external `$ref` MUST use the exact resource ID. Version dispatch selects matching assets; distinct drafts can coexist in one registry. Old inputs MUST be rejected rather than silently upgraded. [Reference implementation](IMPLEMENTATION.md) describes the supported contract and review limits. No public release, adoption, certification or license change is implied.

## 12. Conformance claim form

A BXP-CALC claim has this form; IR and RELAY claims MUST name their own applicable versioned tests, not imply that calculation vectors validate those classes:

```text
Implementation <name/version> passed BXP-CALC for BXP-0001
protocol 0.3.0-draft.2 with BXP-CALC conformance suite 1.0.0-draft.3.
```

Passing means every frozen vector produced the complete required `boundx-result/v1` envelope, not only the same headline verdict or finding codes. It does not mean “zero defects”, “certified”, “safe to execute” or “approved by BoundX” unless a separate authorized certification program exists.
