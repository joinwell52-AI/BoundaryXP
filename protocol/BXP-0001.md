# BXP-0001: Boundary Xplain Protocol

## Abstract

The Boundary Xplain Protocol (BXP) standardizes the expression, formalization and deterministic evaluation of task boundaries.

BXP does **not** treat 7+1 as the protocol endpoint. The 7+1 structure is the standard semantic intermediate representation that carries recognized task semantics into a formal boundary model. The protocol endpoint is a deterministic **Boundary Result**: a machine-readable, referenceable, exchangeable, replayable and freezable representation of the task boundary produced from that formal model.

The normative processing model is:

\[
\text{Task Semantics}
\rightarrow
IR_{7+1}
\rightarrow
\mathcal{M}(IR)
\rightarrow
\mathcal{B}
\]

where:

- `Task Semantics` is the set of task meanings already recognized from source material;
- \(IR_{7+1}\) is the BXP semantic carrier;
- \(\mathcal{M}(IR)\) is the formal boundary model derived from the IR;
- \(\mathcal{B}\) is the deterministic Boundary Result.

BXP does not prescribe whether semantic recognition is produced by HanLP, spaCy, another NLP system, rules, a language model or a human reviewer. Those are producer concerns. BXP standardizes what must be represented, how uncertainty is preserved, how formal constraints are evaluated, and how the resulting boundary is identified and exchanged.

## 1. Status and conformance language

This document is a repository draft. It is not an IETF RFC, an adopted industry standard, a certification program or a publication authorization.

The key words MUST, MUST NOT, REQUIRED, SHOULD, SHOULD NOT, MAY and OPTIONAL are normative requirements of this draft.

This `0.4.0-draft.1` revision redefines the protocol around the Boundary Result as the final standard object. Matching wire schemas, conformance vectors and reference implementation changes are not yet issued. Therefore no implementation may claim conformance to `0.4.0-draft.1` until those assets are versioned and published in this repository.

## 2. Protocol purpose

BXP exists to convert recognized task semantics into a deterministic boundary that can be verified and reused without repeatedly reinterpreting the original natural language.

Let a task semantics object be denoted by \(S\). BXP defines the transformation:

\[
S
\xrightarrow{Normalize}
IR_{7+1}
\xrightarrow{Formalize}
\mathcal{M}
\xrightarrow{Evaluate}
\mathcal{B}
\]

The protocol goal is therefore not merely structural extraction. It is the production of \(\mathcal{B}\), a formal boundary result that another system can reference, compare and validate.

The protocol MUST preserve a strict distinction between:

1. semantic recognition;
2. semantic representation;
3. formalization;
4. deterministic evaluation;
5. business or execution decisions.

BXP covers stages 2–4. Stage 1 may be implemented by different producers. Stage 5 remains outside BXP authority.

## 3. Layer 1 — 7+1 semantic carrier

The 7+1 semantic intermediate representation is:

\[
IR_{7+1}=(I,O,A,P,R,V,C,B)
\]

with the following fixed meanings:

| ID | Name | Normative meaning |
|---|---|---|
| I | Input | Objects, data, systems, populations or other task inputs and in-scope subjects. |
| O | Output | Declared deliverables or externally observable results. |
| A | Actions | Required, permitted or otherwise task-relevant operations, preserving actor, effect, target and modality where known. |
| P | Participants | Humans, Agents, systems and services participating in execution, approval, observation, review, receipt or collaboration. |
| R | Resources | Quantitative limits, budgets, capacities, deadlines, durations and thresholds. |
| V | Version / Provenance | Controlling versions, policies, evidence sources and temporal baselines. |
| C | Completion | Completion, stop, acceptance and escalation conditions. |
| B | Forbidden Boundary | Prohibited effects, targets, actions or combinations, including their guards and exceptions. |

The 7+1 structure is a semantic coordinate system, not the final mathematical boundary.

Formally:

\[
IR_{7+1} \neq \mathcal{B}
\]

A conforming implementation MUST NOT describe a populated 7+1 structure by itself as the final Boundary Result.

Each element MUST preserve explicit uncertainty using at least the states `resolved`, `unresolved` and `absent`. No producer confidence score, default domain assumption or model preference may silently convert an unresolved interpretation into a resolved one.

## 4. Evidence and semantic identity

Every resolved or unresolved semantic claim MUST remain traceable to source evidence.

Evidence establishes where a submitted semantic claim came from. Evidence alone does not prove that the interpretation is complete, unique or correct.

A producer MUST preserve ambiguity if multiple materially different interpretations remain possible. If different interpretations would produce different formal models or different Boundary Results, the ambiguity is boundary-relevant and MUST NOT be collapsed by guesswork.

Let \(I_1, I_2, \dots, I_n\) be admissible semantic interpretations of the same source. If:

\[
\mathcal{B}(I_i) \neq \mathcal{B}(I_j)
\]

for any \(i \neq j\), then the boundary is underdetermined until the ambiguity is resolved by new evidence, clarification or an explicit authoritative choice outside the evaluator.

## 5. Layer 2 — Formal Boundary Model

The semantic IR MUST be transformed into a formal model before deterministic boundary evaluation.

BXP defines the abstract model:

\[
\mathcal{M}(IR)=
(E,\Sigma,Q,F,K,\mathcal{R},D,\Phi)
\]

where:

- \(E\): identified entities and artifacts;
- \(\Sigma\): explicit scopes and state slices;
- \(Q\): required outcomes and obligations;
- \(F\): forbidden actions, targets, effects or state combinations;
- \(K\): completion and stopping conditions;
- \(\mathcal{R}\): participant, role and relation facts;
- \(D\): dependency, handoff, provenance and version relations;
- \(\Phi\): formal constraints such as numeric, set, logical, temporal or ordering predicates.

This tuple is an abstract protocol model. A wire representation MAY encode it using multiple typed collections rather than one literal tuple.

Examples of formalization include:

\[
\text{“duration must not exceed 10 minutes”}
\Rightarrow
 duration \le 600s
\]

\[
\text{“without ADMIN approval, publishing is forbidden”}
\Rightarrow
\neg approved_{ADMIN} \Rightarrow \neg publish
\]

\[
\text{“the production database must not be modified”}
\Rightarrow
ModifiedTargets \cap ProductionDatabase = \varnothing
\]

Formalization MUST NOT invent facts absent from the semantic IR. If identity, unit, scope, relation or applicability is not determined, the formal model MUST preserve that lack of determination instead of manufacturing a computable value.

## 6. Layer 3 — Boundary evaluation

Boundary evaluation applies a versioned operator profile \(O_v\) to a formal model:

\[
\mathcal{B}=Evaluate(\mathcal{M},O_v)
\]

For identical \(\mathcal{M}\) and identical \(O_v\), the evaluator MUST produce the same \(\mathcal{B}\).

\[
\mathcal{M}_1=\mathcal{M}_2 \land O_{v1}=O_{v2}
\Rightarrow
Evaluate(\mathcal{M}_1,O_{v1})=Evaluate(\mathcal{M}_2,O_{v2})
\]

Evaluation MUST NOT depend on random sampling, wall-clock time, model temperature, network responses or other undeclared external state.

### 6.1 Operator profiles are mechanisms, not the protocol core

BXP may define or register multiple deterministic operator families. Examples include:

- interval algebra;
- typed-set overlap and difference;
- handoff and data-flow deficit;
- prerequisite and dependency graph checks;
- propositional logic;
- temporal constraints;
- ordering constraints;
- cardinality constraints;
- identity and equivalence constraints;
- reachability;
- resource constraints;
- version and provenance checks.

The availability of one particular operator family does not define BXP itself. Operator families are versioned methods used to evaluate the formal boundary model.

An operator family MUST have deterministic semantics, bounded input rules, explicit unresolved behavior and machine-testable output.

## 7. Layer 4 — Boundary Result

The Boundary Result is the final protocol object.

A Boundary Result MUST answer two questions:

1. **Is the task boundary determined?**
2. **If it is determined, what is that boundary?**

The abstract result is:

\[
\mathcal{B}=
(State,
Required,
Forbidden,
Limits,
Completion,
Relations,
Dependencies,
Provenance,
Findings)
\]

A wire schema MAY organize these components differently, but it MUST preserve their semantics and deterministic identity.

### 7.1 Boundary state

A Boundary Result MUST expose one of the following protocol states or an equivalent versioned representation:

- `determined` — the boundary-relevant semantics and identities required by the active profile are resolved, the formal model is valid, and all required evaluation results are deterministic and non-conflicting;
- `underdetermined` — unresolved semantics, identity, scope, unit, applicability or other uncertainty can materially change the Boundary Result;
- `inconsistent` — the model is sufficiently determined to prove that submitted requirements cannot all hold together;
- `invalid` — the submitted protocol data is structurally or semantically invalid and no valid boundary may be produced.

A result MUST NOT use `determined` merely because calculation code finished.

One abstract condition for determination is:

\[
Determined(\mathcal{B})=
Valid
\land RequiredResolved
\land IdentityResolved
\land ScopeResolved
\land NoBoundaryRelevantAmbiguity
\land Consistent
\]

Profiles MAY refine this condition but MUST NOT weaken uncertainty preservation.

### 7.2 Accuracy

BXP accuracy means exact evaluation of the supplied formal model and the absence of false certainty.

If semantics remain ambiguous in a way that can change the result:

\[
Ambiguous \not\Rightarrow ChooseMostLikely
\]

Instead:

\[
Ambiguous \Rightarrow underdetermined
\]

BXP does not claim that a parser or NLP producer always understands natural language correctly. Extraction quality requires separate evidence and conformance criteria. BXP does require that the evaluator never disguise known uncertainty as a determined boundary.

## 8. Referenceability, exchangeability and freezing

Boundary Results are intended to be stable data objects, not prose advice.

A conforming result model SHOULD bind at least the following identities:

\[
D_S=Hash(Source)
\]

\[
D_{IR}=Hash(IR_{7+1}+FormalizationInputs)
\]

\[
D_M=Hash(Canonical(\mathcal{M}))
\]

\[
D_B=Hash(Canonical(\mathcal{B}))
\]

where \(D_B\) is the boundary identity (`boundary_digest`).

Any change that changes the deterministic Boundary Result MUST change \(D_B\).

A Boundary Result is **referenceable** when a downstream system can bind to its protocol version and \(D_B\) without reinterpreting natural language.

A Boundary Result is **exchangeable** when another implementation can validate its schema, protocol version, operator profile and digests without requiring the same NLP engine or producer implementation.

A Boundary Result is **freezable** when its exact inputs, operator profile and canonical result identity are pinned so later source, IR, formalization or operator changes cannot silently mutate the referenced boundary.

A Boundary Result is **replayable** when an independent conforming evaluator can recompute:

\[
Evaluate(\mathcal{M},O_v)=\mathcal{B}
\]

and obtain the same canonical result identity.

## 9. Producer independence

BXP does not standardize a particular semantic recognition engine.

A producer MAY use:

- HanLP;
- spaCy;
- another NLP framework;
- deterministic rules;
- statistical models;
- neural models;
- an LLM;
- human annotation;
- a combination of these.

Producer choice MUST NOT change the meanings of I/O/A/P/R/V/C/B or the formal semantics of the Boundary Result.

Different producers that submit semantically equivalent IR and formalization inputs SHOULD converge to the same Boundary Result under the same operator profile.

## 10. Downstream conformance

A Boundary Result is designed to serve as a reference baseline for downstream plans, decompositions or implementations.

For a downstream object \(X\), a consumer may evaluate:

\[
Conform(X,\mathcal{B})
\]

Typical comparisons include:

\[
Missing = Required_{\mathcal{B}} \setminus Covered_X
\]

\[
Violation = Actions_X \cap Forbidden_{\mathcal{B}}
\]

and constraint satisfaction:

\[
X \models \Phi_{\mathcal{B}}
\]

BXP does not require the downstream consumer to be a PM, Agent, workflow engine or human team. It standardizes the boundary data that such consumers may reference.

## 11. Current standard operator profile

The existing BXP implementation lineage includes the following deterministic operator families. They remain useful, but they are implementation/profile methods rather than the definition of BXP.

### 11.1 Profile completeness

\[
Deficit=Required(profile)\setminus Resolved(IR)
\]

A non-empty deficit means required semantic coverage is missing or unresolved. An empty deficit does not by itself prove extraction correctness.

### 11.2 Interval intersection

For compatible interval identities:

\[
L=\max_i L_i,\qquad U=\min_i U_i
\]

The intersection is empty when \(L>U\), or when \(L=U\) and an endpoint is open.

### 11.3 Typed-set overlap

\[
Overlap=RequestedTargets\cap ForbiddenTargets
\]

A non-empty overlap is a deterministic boundary conflict for the submitted identity and scope.

### 11.4 Handoff deficit

\[
Available=DeclaredOutputs\cup ExternalInputs
\]

\[
Missing=RequiredInputs\setminus Available
\]

### 11.5 Dependency consistency

A mandatory prerequisite relation is inconsistent when its directed graph contains a cycle.

### 11.6 Propositional consistency

For a resolved scope, all submitted formulas and assumptions are conjoined. The result is satisfiable when at least one valuation exists and unsatisfiable otherwise.

These operator families MAY evolve independently under versioned operator profiles, provided protocol determinism and result semantics remain intact.

## 12. Authority boundary

A Boundary Result describes computed task-boundary facts. It does not itself make a business decision, grant permission, authorize execution, prove legality, prove safety or prove task completion.

Every conforming wire result that exposes authority fields MUST preserve the equivalent of:

```json
{
  "business_decision": null,
  "execution_authorization": null
}
```

No BXP conformance class may redefine a determined boundary as an execution authorization.

## 13. Versioning and migration

Draft versions use `MAJOR.MINOR.PATCH-draft.N`.

`0.4.0-draft.1` changes the conceptual center of BXP from “7+1 plus a fixed set of calculations” to the four-layer model:

\[
\boxed{
TaskSemantics
\rightarrow
IR_{7+1}
\rightarrow
FormalBoundaryModel
\rightarrow
BoundaryResult
}
\]

This draft intentionally does not claim that the current `boundx-task/v1`, `boundx-result/v1` schemas or existing frozen vectors already implement all new Boundary Result identity and state requirements. A later implementation task must version the affected schemas, operator profile, conformance suite and migration rules before `0.4.0-draft.1` can be claimed as implemented.

Existing `0.3.0-draft.2` wire behavior remains historical implementation evidence and MUST NOT be relabeled as `0.4.0-draft.1` conformance.

## 14. Core definition

The stable core of BXP is not 7+1 by itself and is not any particular calculation algorithm.

The stable core is:

\[
\boxed{
IR_{7+1}
\rightarrow
\mathcal{M}(IR)
\rightarrow
\mathcal{B}
}
\]

BXP uses a standard semantic carrier to construct a formal task-boundary model and deterministically produces a Boundary Result that is accurate with respect to the supplied formal model, referenceable, exchangeable, freezable and replayable.

7+1 exists to serve formalization.

Formalization exists to serve deterministic evaluation.

Deterministic evaluation exists to produce the Boundary Result.

The Boundary Result is the protocol endpoint.
