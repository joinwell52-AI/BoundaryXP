# BoundX Protocol Governance Draft

状态：`DRAFT_FOR_REVIEW`。本文件不授权公开发布、认证或商标许可。

## 1. 单一协议与资产边界

界痕（BoundX）只有一套 7+1 核心语义。协议、Schema、一致性向量、自然语言抽取器和三层语义包不能各自重新定义 I/O/A/P/R/V/C+B。

- `BXP-0001`：协议语义的规范来源。
- `schemas/`：协议语义的机器可读投影。
- `conformance/`：规范行为的可重复验证。
- `domain-packs/`：同一 IR 的词汇与归一化插件，不是平行协议。
- BoundX 引擎：协议实现，不因“官方实现”取得业务裁决权。

## 2. 变更分类

| 类型 | 示例 | 要求 |
|---|---|---|
| Editorial | 错字、链接、非规范说明 | 两人复核，不改变测试结果 |
| Patch | 不改变可接受输入或计算语义的文字／测试修正 | 增加必要回归，提升 PATCH；行为变化不得归为 Patch |
| Additive | 新可选算子、新符合性等级 | 公开评审，提升 MINOR |
| Breaking | 改字段含义、删除状态 | 新 MAJOR，不静默迁移 |
| Core semantic | 重定义 7+1、裁决权或证据原则 | 必须提交独立 BXP 提案并由 ADMIN 明示采用 |

1.0 前按 BXP-0001 §11 执行草案例外：不兼容修订可提升 MINOR，但必须固定精确草案版本、记录兼容性变化、更新 Schema 与向量并保留旧 Git 基线。Schema 与文字不一致若改变有效输入或结果，必须按实际行为影响分类，不能以“修错”为由静默改变合同。当前仓库保持私有，公开评审／采用／发布必须另获 ADMIN 授权；内部修订不自动满足两人复核或公开评审要求。

## 3. 提案流程

1. 提案必须有唯一编号、动机、范围、威胁模型和兼容性说明。
2. 规范变化必须同时提交 Schema、正反测试向量和迁移影响。
3. 抽取准确率或单个行业需求不能直接修改核心语义，优先进入 Profile 或命名空间扩展。
4. 评审必须公开记录未解决异议，不能用“测试通过”替代语义采用。
5. 只有 ADMIN 的明确采用记录才能把 Draft 提升为 Adopted；Git 合并本身不等于协议发布。

## 4. 版本状态

```text
Proposal → Draft → Implementer Review → Candidate → Adopted
```

各状态独立于产品 Release。协议进入 `Adopted` 不会自动发布商业引擎，产品发布也不会自动升级协议。

## 5. 独立实现与互操作

升级为 1.0 Candidate 前，应至少具备：

- 两个独立实现；
- 对同一规范向量的字节级或字段级一致结果；
- 至少一次跨实现互操作记录；
- 已公开的歧义、失败和未实现项；
- 自然语言抽取与确定性计算分开的评测报告。

## 6. 扩展注册

第三方扩展使用其控制域名的反向域命名空间。`org.boundx.*` 由 BoundX 协议维护者保留。扩展不得覆盖核心字段，不得将 `null` 的业务决定或执行授权改写为自动结论。

## 7. 一致性声明

仓库测试结果只能形成版本化自测声明。正式认证、徽章、公共注册表和撤销程序必须由另行采用的认证政策建立；在此之前不得使用“BoundX Certified”。
