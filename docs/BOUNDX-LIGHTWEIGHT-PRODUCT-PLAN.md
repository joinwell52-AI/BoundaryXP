## 1. 一句话定位

**界痕（BoundX）是一个可嵌入、可服务化的任务边界防呆校验工具：先把散装指令收敛成 7+1，再用确定性规则检查缺项、冲突、越界和流程依赖，最后输出可追溯的结果或干净工单。**

它不需要承担“行业标准”“全球协议竞争”或“通用自然语言理解平台”的宏大目标。BXP-0001 保留为工具内部稳定的数据合同和计算说明，不作为首版销售话术的中心。

## 2. 用户实际看到什么

### 2.1 输入

用户粘贴原始任务，再通过一页表单核对八项内容：

| 字段 | 用户问题 |
|---|---|
| I | 处理什么对象，范围到哪里？ |
| O | 最后交付什么？ |
| A | 允许执行哪些动作？ |
| P | 谁执行、谁审批、谁接收？ |
| R | 时间、金额、数量、调用量等上限是什么？ |
| V | 依据哪个制度、版本或数据来源？ |
| C | 满足什么条件才算完成或停止？ |
| B | 哪些动作、对象或条件绝对不能碰？ |

自然语言抽取只负责提出候选并标出原文，不能静默替用户确认。没识别出来就留空并要求补充，不用模型概率伪装成确定事实。

### 2.2 确定性计算

首版只做几类普通用户能理解、程序能够确定复算的检查：

- 必填内容是否缺失；
- 时间、金额、数量等上下限是否形成空区间；
- 操作对象是否命中禁止名单；
- 上游产物能否满足下游输入；
- 必须先后执行的步骤是否成环；
- 授权条件与强制动作是否在某个状态下互相冲突；
- 原文证据位置是否真实对应输入文本。

程序输出“未发现结构问题”“发现确定冲突”或“需要补充/澄清”，但不输出业务批准，不验证现实身份，也不授予执行权限。

### 2.3 输出

用户最终获得：

1. 原始任务与证据引用；
2. 已确认的 7+1；
3. 可复算的检查结果；
4. 需要修改或确认的具体位置；
5. 一张可复制、下载或提交给现有系统的结构化工单。

产品主线可以概括为：

> 表单收敛输入，数学把关边界，代码保证执行。

其中“代码保证执行”是指宿主系统按照已确认工单执行；BoundX 本身不直接操作生产资源。

## 3. 首版适用场景

首版不追求覆盖所有行业，优先寻找“规则不多、出错代价明显、负责人能直接决定购买”的小场景。

| 场景 | 常见问题 | BoundX 的作用 |
|---|---|---|
| 小型运维团队 | 误删分支、误碰生产库、时间窗口不清 | 在执行前检查目标、禁止对象、审批条件和回滚要求 |
| 车队或调度 | 车辆、司机、路线、金额和时限交代不清 | 把对象、动作、额度和禁止事项写成固定工单 |
| 仓库管理 | 调拨数量、目标库位、危险品规则混乱 | 检查数量区间、名单冲突和交接缺口 |
| 售后与退款 | 退款额度、审批人、证据和完成条件缺失 | 在提交现有业务系统前做防呆核对 |
| 小型 AI/软件团队 | Agent 接到模糊指令后扩大范围 | 明确仓库、动作、资源、版本、完成条件和禁止边界 |

涉及金融、医疗、法律、安全生产等受监管事项时，BoundX 只能作为内部结构检查，不能替代专业合规系统、持证人员判断或法定审批。

## 4. 最小可卖产品

### 4.1 公共工具

第一版目标是形成一个完整的小工具；以下命令尚未完成 PyPI 发布，不能作为当前可用能力宣传：

```text
pip install boundx
bx serve
```

既可打开 Web 页面填单和检查，也应保留：

```text
bx check task.json
bx export task.json --format markdown
```

首版验收标准：

- 新用户十五分钟内能安装并跑通示例；
- 本机模式默认只监听本机地址；服务器模式使用独立认证与部署配置；
- 没有 Python/依赖错误时明确失败，不伪装成功；
- 三个演示任务可以从填写、检查走到工单导出；
- 中文证据位置不乱码；
- 相同结构化输入得到相同结果；
- 不执行退款、删除、发布、付款等外部动作。

### 4.2 三个公开 Demo

公开仓库只需提供三个容易理解的演示规则：

1. 退款金额不得超过 500 元，超过时要求审批；
2. 清理分支不得包含 `main` 和受保护发布分支；
3. 运维操作必须先生成快照，未生成时不得覆盖写。

Demo 用于让用户五分钟理解产品，不包含真实客户规则，也不冒充行业合规方案。

### 4.3 保留的定制资产

以下内容不随公共工具上传：

- 车队、租售、违章、退款、仓储等真实行业规则包；
- 企业内部角色、审批链、额度和别名表；
- 客户原始规程、工单、日志和数据；
- 高精度自然语言抽取规则与人工整理经验；
- 私有边缘测试与调优数据。

公共代码负责“怎么算”，付费定制解决“客户自己的规则究竟是什么、怎样安全地写进去”。

## 5. 两种简单收费方式

### 5.1 作为集成项目的增值模块

在已有系统集成、自动化、运维或管理软件项目中，把 BoundX 作为任务提交前的防呆模块：

- 安装本地工具；
- 梳理一组客户高频规则；
- 配置角色、额度、禁止对象和工单模板；
- 接入客户已有系统的导入/导出；
- 提供一次培训和验收。

价格假设：在原项目报价上增加人民币 8,000—15,000 元。该区间只用于验证客户意愿，不写成长期公开价目表。

### 5.2 单独的小型定制交付

适合规则不多、单机或内网使用的小客户：

- 安装与配置；
- 整理 10—30 条规则；
- 制作一套表单和工单模板；
- 培训一名负责人；
- 约定一次小版本修正。

价格假设：简单项目人民币 3,000—5,000 元；角色、流程和系统接口明显增加时另行报价。是否可行应通过前三个真实客户验证，不能把假设写成已经实现的收入。

## 6. 最省心的开源方案

### 6.1 发布许可提案：GNU AGPL v3

BoundX 已作为独立产品维护，当前根目录 [LICENSE](../LICENSE) 为 MIT。拟议公开版本采用 GNU AGPL v3（候选 SPDX `AGPL-3.0-only`），这仍是未生效提案，而不是当前许可证。

公开前须核对资产权属、依赖兼容性、版权声明及完整许可证文本，并取得明确批准。客户 L3、商业语义包、密钥、真实工单和未授权材料不得公开。商业 Pack 的组合与分发方式需另行核对。

### 6.2 首次公开范围

建议公开：

- 轻量确定性计算内核；
- Python、CLI、MCP、Server 和 Web 表单；
- BXP 结构、Schema 和 BXP-CALC 公共测试；
- 三个 Demo 规则；
- 安装、使用、贡献和安全说明。

建议保留：

- 行业规则包；
- 客户 L3 配置；
- 商业连接器；
- 高精度抽取规则；
- 私有挑战集。

### 6.3 数字来源只做必要部分

首版保留以下来源证明已经足够：

- Git 提交历史；
- Release Tag；
- 发布文件 SHA-256；
- Manifest；
- 版权与许可证声明。

不在计算里埋秘密 epsilon、魔数、错误舍入或隐藏文法。别人原样复制时，版权声明、代码结构、文件摘要和历史提交可以共同形成线索；独立实现相同协议得到相同结果不等于复制。

## 7. README 的正确销售口径

首页首先回答三个问题：

### 它是什么？

一个本地任务边界检查工具，带表单、CLI 和规则包接口。

### 它解决什么？

把群聊、口头和自然语言中的散装任务整理成明确工单，在执行前发现缺项、数值矛盾、禁止对象碰撞和步骤死循环。

### 怎样跑？

```text
pip install boundx
bx serve
```

首屏不使用“行业事实标准”“全球协议”“数学证明一切安全”“100% 防事故”等表述。可以如实说明：结构化计算已有 208 条一致性向量，但自然语言抽取能力必须单独评测。

## 9. 三步推进

### 第一步：把产品跑顺

- 把现有 Node/Python 能力整理为真正的一条安装命令；
- 固定本地表单、检查、修改、重新计算和导出工单流程；
- 用三个 Demo 做干净机器验收；
- README 只写实际跑通的功能。

### 第二步：找三个真实小客户

- 每个客户先挑 10—30 条最容易出错的规则；
- 记录整理规则、配置、培训和修正所需工时；
- 验证 3,000—5,000 元和集成增价 8,000—15,000 元是否能成交；
- 记录客户真正愿意付钱的是表单、规则、对接还是售后。

### 第三步：再决定是否做大

只有出现重复客户需求以后，才把共性规则整理成 L2 行业包；只有出现稳定下载和第三方实现以后，才投入更多协议治理。产品规模由真实使用拉动，不由文档想象推动。

## 11. 结论

BoundX 先做好一件小事：**让一条准备交给人、脚本或 Agent 执行的任务，在提交前把对象、动作、责任、上限、依据、完成条件和禁止边界说清楚。**

开源代码是技术名片，行业规则是定制资产，安装和规则整理是近期收入。先让工具在真实客户环境中稳定工作，再决定它未来需要多大的协议、生态和商业体系。
