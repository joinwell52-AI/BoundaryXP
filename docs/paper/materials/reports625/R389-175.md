## 三、形式模型

工单采用实际查得的 L2 含义：software-ai@0.2.0，/entities/51，ticket，是 work-item。词典没有授予访问或审批权限。对“栖云工单台”“audit-private”“shared-summary”的所选 L3 查询均未命中；对象及权限关系直接采用正文，不从未命中推导新身份、同名映射或未知授权。

令 $U=\{S01,S02,S03\}$，表示本轮允许输入的脱敏工单标识集合，来源 E5。令 $D=\{S04\}$，仅表示 DEV 明确新增的读取请求，来源 E18；它不是对 DEV 全部实际读取行为的枚举。S04 的“脱敏”属性已明确，但对象标识仍不属于 $U$。

将本轮具体计划限制写为 $Q_j$：角色 $j$ 不新增集合外工单请求，不新增原始库访问、受禁目录读取、未脱敏结论共享或系统落地修改，不替换整体交付与证据职责，不代批、不伪造状态、不取消适用继承。计算中使用各角色新增安排的具体属性，而不把父规则简单复制后宣称已符合。角色自己的有限任务文本是本次新增安排的比较范围；没有新增访问动作，表示该文本没有提出该动作，不表示现实访问未发生。

输入使用事件的稳定身份为 act-dev-S04-use，主体 DEV、对象工单 S04、范围为本轮复现。QA 的记录动作与它不同；两个整理岗位的编排动作也与它不同。对已述使用事件，令 $u$ 表示该使用事件已被正文报告，$m$ 表示其对象属于 $U$。E31 给出 $u=true$，E5 与 E31 给出 $m=false$。父条件为 $u\Rightarrow m$。本例是无额外触发前置的输入范围限制，不引入“新增请求”替代已述事件。

PM 冻结、汇总及向 ADMIN 报告是 PM 自有职责。另以各后代是否提出改派、取消或覆盖这些职责比较责任非干涉。DEV 自有准备职责与 QA 自有复核、汇报职责也采用相同的责任范围处理。

## 四、数学计算一

先比较同一属性——工单标识——上的允许集合和明确新增请求：

$$D\subseteq U.$$

代入正文：

$$\{S04\}\setminus\{S01,S02,S03\}=\{S04\}\ne\varnothing.$$

因此 DEV 的新增读取请求不满足集合包含关系（K1）。违反见证就是 E18 的 S04，无须知道运行日志、实际耗时或某个自然人姓名。已脱敏只能满足数据形态要求，不能改变工单标识的集合成员关系。标题 E1 没有修改这一正文集合。

OPS 的容器是另一类对象。E27 明确将其处理范围限定于三个允许标识所对应的容器；本分析不把“容器”等同“工单副本”，也不从处理容器推定已经读取工单。其任务书没有提出 S04、新目录读取或落地修改，相关父限制继续继承（K4）。

## 五、数学计算二

具体方案比较将“明确新增的不合规安排”作为命题属性，检查父边界要求其为假。DEV 的非输入部分没有提出原始库访问、受禁目录读取、个人字段共享、落地修改、代批或伪造实施事实；其工件和交接清单是中间交付，没有取消整体报告、建议或证据义务（K2）。但这一局部保持不能抵消 K1 的集合违反。

DEV 文档整理员只编排交来材料，不代造报告、不改变版本和工作安排（E21—E24）；这既没有把 DEV 的 S04 安排改成合规，也没有提出自己读取 S04。其具体新增动作与访问动作不同，局部符合性成立（K3）。QA 如实记录并不补批准；QA 证据复核员只保留引用、注明缺失且不自行批准或宣告整体完成（K5、K6）。五个后代都没有改派或取消 PM 的冻结、汇总和报告职责（K7）。

再独立评估已述事件：

$$P=u\Rightarrow m,\qquad F=u\land\neg m.$$

代入 $u=true,m=false$：

$$P=false.$$

所以 E31 报告的 DEV 使用 S04 事件与父输入限制冲突（K8）。这不是把 DEV 的拟议读取当成已执行；事件证据独立来自 QA 正文的“使用了”。QA 是报告者，事件操作者仍是 DEV。

## 六、关键区别与可满足性

规则保持：OPS、两个整理岗位与 QA 没有提出突破各自适用父限制的新增要求。DEV 其余限制可以保持，但其新增 S04 请求已构成局部确定违反。整理岗位“不改变已声明工作安排”要求忠实保存来源，不是替 DEV 授权，也不是要求整理员执行该安排。

文本事实条件：K8 的两个变量均有正文赋值，没有需要补全的事实变量；唯一给定赋值 $(u,m)=(true,false)$ 违反条件。若将对象改成 S01，则 $(true,true)$ 可以符合，但这会改变原文对象，不能作为本案的允许补全。假设另有批准也不能改变 E5：原文没有设置“经批准可新增工单”的例外。

父规则可满足不等于当前子方案符合。仅使用允许工单的方案是父规则的满足见证；当前 DEV 明确请求 S04 是子方案的违反见证。其他角色的记录、资料编排和证据复核无需新增工单读取，能够与父限制同时成立。

本例没有应当填成 null 的具体已述事实变量。“未报告实际完成”不被升级为任务书不合规；关于可能缺失材料的处理要求也不被转成已经缺失的事实。没有前置证据不足的 READINESS 查询需求。

## 七、最终结果

各子任务规则边界：DEV 越界，见 E5、E18、K1；DEV 文档整理员、OPS、QA、QA 证据复核员未越界，分别见 K3、K4、K5、K6。各自结论只评价其任务书新增要求与适用父边界。

文本已述事实／证据符合性：QA 报告的 DEV 使用 S04 事件违反输入集合限制，见 E31、K8；没有据此认定 QA 或整理岗位是该使用事件的操作者。

综合结论：任务书越界；完整文本综合越界。DEV 的确定违反不否定其他角色局部保持边界的结果，其他角色的局部保持也不能抵消 DEV 的违反。

来源措辞校正：标题“新增第四条工单”只能作为主题。正文没有给出扩大集合的许可；“如实记录”不能改写成“替 DEV 批准”，保留原工作安排也不能改写成执行该安排。

建议：删除 DEV 额外读取 S04 的拟议要求，将比较限定在三个允许副本内；已述使用事件仍如实保留，不追写成已有批准。若拟改变输入边界，应另行明确修改有权来源的正文规则，本分析不提供该业务批准、实际验收或执行授权。
