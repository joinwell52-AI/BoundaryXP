## 三、形式模型

令本轮作用域为 $\Sigma$。输入实体集合为 $S=\{S01,S02,S03\}$，其属性是“脱敏副本”；目录对象分别记为 $D=$ audit-private、$H=$ shared-summary，客户原始库记为 $R$。这三个对象不因同属资料来源就合并。

定义关系 $L(r,a,o,\Sigma)$ 表示本轮角色 $r$ 对对象 $o$ 的动作 $a$。父文给出 $L(QA,read,D,\Sigma)$ 的许可，并禁止 $L(DEV,read,D,\Sigma)$ 与 $L(OPS,read,D,\Sigma)$。允许的共享路径是 QA 将去除个人字段的结论写到 $H$，供 DEV 使用；该路径不等于允许 DEV 读取 $D$。没有具体制品版本号，因此不制造版本身份，也不把版本缺省解释为执行失败。

对各角色的完整拟议安排，定义六类具体改动指标：$a$ 为是否安排 DEV 或 OPS 直接读取 $D$；$b$ 为是否新增超出 $S$ 的输入或访问 $R$；$c$ 为是否取消总体交付或提出本轮落地修改；$d$ 为是否覆盖 PM 冻结、各角色证据保存或适用的来源记录要求；$e$ 为是否改派或取消父角色自有职责，或增加代审批、转授权限；$f$ 为是否要求补造、隐瞒未提供信息或把建议写成已实施。两名下级另用 $g$ 检查其具体编排范围是否偏离直属父级分工。

这些指标描述本次文本提出的动作和改写，给定值不是运行事实。特别是 $a=false$ 只表示该角色没有提出对应读取安排，不表示已经核实其现实中从未读取。

实际采用的 L2 词义包括 permission（software-ai@0.2.0，/entities/28：访问权属于权限对象）、grant_permission（/frames/31：授予权限是一项 CHANGE 动作）与 handoff（/frames/27：交接属于 SEND）。因此记录交接与授予访问权不能合并。L3 开发岗位定义（tenant-a@0.2.0，/positions/2）与测试岗位定义（/positions/3）也不能把岗位、具体任职者和任务签字人混成一个身份。本例按正文明确的 DEV、QA、OPS 角色判断，不从多个名册候选中选择自然人。

audit-private、shared-summary 在所查企业包中均未命中；正文已经明确它们之间的权限和输出关系，未命中不削弱这些关系，也不产生额外授权。

## 六、关键区别与可满足性

**规则保持：**DEV 文本中“不把建议写成已经实施”“文档整理不增权限”等规则可以保持，但不能推出 DEV 全案合规。父文没有给“协助 QA”设置例外，QA 自行复核也不是 DEV 私有读取禁令的解除条件。

**文本已述状态：**本例没有明确报告读取已完成、审批已授予或某前置当前未满足。接收记录的拟议安排不反推记录已存在，更不反推读取已经发生。因此不构造 OCCURRED_ACTION，也不另造一次 READINESS 查询来要求执行回执。

**未知补全：**假设未来 QA 确实自行复核，DEV 的直接读取安排仍违反 E07；假设 QA 未进行复核，直接读取安排仍违反 E07。再假设共享摘要已去除个人字段，也只能支持对应共享路径，不能使直接读取 $D$ 合规。这些反例用于说明结论独立性，不作为本例新增事实变量。

父规则自身存在符合解释：使用 $S$ 的脱敏副本，PM 冻结数据包，各角色保存证据，QA 在需要时读取私有目录并仅共享去除个人字段的结论，DEV 使用共享结论形成建议，本轮不修改，PM 汇总报告。QA 的两个许可也可以不使用，不能误读成必须读取和必须写摘要。这个可满足示例没有要求每个下级完成父角色的工作。

DEV 文档整理员“保留已声明的工作安排”是来源保存要求。忠实记录 E18 的违规内容与亲自执行 E18 不同；该整理要求不能改写 DEV 的违反结果，也不构成整理员直接读取的证据。
