## 三、形式模型

固定本轮版本1，令角色集合 $U=\{DEV,OPS,QA\}$，交接根目录为 $W$，原始快照为 $S$，待交接实现为 $V_D$。$S$ 与 $V_D$ 是待绑定的对象身份，不能因路径或摘要尚缺就任选文件代入。

对角色 $u$ 定义 $d_u$ 为连接本轮交易数据库，$f_u$ 为触发实际退款，$w_u$ 为遵守 $W$ 下输入只读及角色产物分目录，$t_u$ 为遵守先提交安排预检、操作后留执行记录的阶段要求。父公共约束为：

$$H=\bigwedge_{u\in U}(\neg d_u\land\neg f_u\land w_u\land t_u).$$

联合交付再定义 $s$ 为正式日报取自提供的脱敏快照，$m$ 为金额处理使用 Decimal，$c$ 为币种分离求和，$o$ 为交付日报、中文说明及可复现样例，$p$ 为 PM 保持交接与收口责任。父模型为：

$$P=H\land s\land m\land c\land o\land p.$$

计算操作数将 $H$ 中逐角色量化的四项分别封装为 $n,r,w,t$。它们仍保留全部角色和本轮对象的联合绑定，不能迁移到其他项目、版本或环境。子方案增加的是局部要求，并未声明撤销 $P$。

DEV 的分组键为 $(merchant,currency)$。同一商户的两种币种属于两个分组，不允许只按 merchant 相加。诊断中的重复号如何处理尚待具体规则；不能自行决定保留第一条或删除全部。

查询所用 L2 词义：software-ai@0.2.0 的 /entities/53 将“快照”归为备份制品；/entities/34 将数据库归为数据对象；/frames/8 将“实现”归为代码变更；/entities/27 将报告归为制品。代码变更并不自动等于连接数据库或触发退款。/frames/60 的“准备环境”动作不能覆盖整句语义：本例要求“准备环境记录与重放步骤”，不能据关键词擅自推出安装包。查询返回的 L3 员工资料和整套系统交付词条均与本例无指称关系，未采用。版本查询返回多个动作候选；本例没有发布动作语境，未把“DEV版本交接”解释为上线发布。

## 四、数学计算一

金额对象是订单行的 refund_amount 属性；量纲为货币金额，单位由每行 currency 给出。不同币种不可因数值相同而直接相加。本例没有汇率、实际金额或时间上限，不能计算真实总额或补造单位换算。

令 $D$ 为在明确去重规则下确定的有效订单行集合，则报表每组应满足：

$$T_{a,b}=\sum_{i\in D:\ merchant_i=a\land currency_i=b}\operatorname{Decimal}(refund\_amount_i).$$

父任务要求的币种总额可由商户明细再聚合：

$$T_b=\sum_a T_{a,b}.$$

因为分组集合按币种互不混合，增加商户维度不会破坏币种隔离。代入本例指定的列，DEV 使用 $(merchant,currency)$，OPS 使用分币种CSV，QA 指定同商户两个币种作为覆盖项，三者方向相容。币种数量为样例覆盖的两个，不是金额为2，也不是正式快照只有两个币种。

没有订单行和具体去重规则，无法给出金额数值；该缺口不影响“联合分组能够保持币种隔离”的结构结论。现有 Core 未提供分组聚合算子，此公式作为可复核语义论证保留，不伪造金额操作数。

对公共边界，令 $C$ 为当前子任务对父约束的继承，则：

$$C=H,\qquad C\Rightarrow H.$$

K1 的 RULE_PRESERVATION 使用有原文来源、仍有效的父规则检查继承。这里没有将未观测的现实行为填成 false，也没有以无依据的真值代替约束。

## 五、数学计算二

将各子任务新增要求记为 $D,O,Q$。按父子任务继承语义，联合方案为：

$$J=P\land D\land O\land Q,\qquad J\Rightarrow P.$$

K2 验证的是保留父义务的联合方案，不能据此证明新增要求已经实现。反例检验如下：若 OPS 为生成报表而连接交易数据库，则 $d_{OPS}=1$，从而 $H=0$；若 DEV 为测试而触发实际退款，则 $f_{DEV}=1$，同样违反 E2。两种行为都没有在当前子方案中提出。相反，自造 QA 样例只要写入 QA 目录、保持 input 不变，就有 $w_{QA}=1$，不构成对 E4 的突破。

事件固定为本轮 $e_D$：DEV 将实现及样例交 OPS；$e_{O1}$：OPS 对该版本第一次运行；$e_{O2}$：同快照第二次运行；$e_I$：本轮交付说明可供 QA 阅读；$e_Q$：QA 阅读后的复核。原文给出：

$$e_D\prec e_{O1}\prec e_{O2},\qquad e_I\prec e_Q.$$

K3 保存上述动作前置并检查所需路径。没有从“复算”凭空增加 $e_Q\prec e_D$，也不把所有角色关系转换为前置边。事件图有顺序赋值 $e_D=1,e_{O1}=2,e_{O2}=3,e_I=1,e_Q=2$，不存在所列前置造成的环。此处整数只是抽象先后序位，不是时间测量。

因此，DEV、OPS、QA 均无已证明的方案突破；PM 仍承担交接与收口。完整性检查仍须等待制品与绑定材料，不能把本节结论提升为执行验收。

## 六、关键区别与可满足性

父规则自身：存在满足赋值，例如所有角色均不连接交易数据库、不触发退款、保护输入并分目录留产物；以提供的快照用 Decimal 分币种生成日报，交中文说明与可复现样例，PM 完成交接收口。因此父规则有非空解空间，不能因尚无运行日志就称父规则矛盾。父一致性依据该满足见证，不依据 K2 的蕴含结果。

父规则加当前事实：节点身份和版本事实没有要求执行禁用动作，仍有上述满足见证。实际快照和解释器尚未给出只形成待绑定信息，不等于它们不合规。

父规则加固定子方案：可在 $W$ 中保留 input，只在 DEV、OPS、QA 各自目录写制品；DEV 实现双键分组并登记摘要，OPS 等交接后在绑定解释器上连续重放两次且不装包，QA 用自造样例核对并记录结果。该见证满足所表达的方案要求，没有理由把代码实现、CSV增加或独立测试当成退款操作。此为存在性证明，不是声称制品已经存在。

两个容易混淆的局部条件：等待 DEV 交接只限制 OPS 运行开始，不表示 QA 的所有准备必须等待 OPS；阅读说明只限制 QA 复核阶段，不禁止其先构造样例。父文“供预检”未规定批准者、批准值或正式准入成功，不能补造审批事实。
