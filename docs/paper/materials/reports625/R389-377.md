## 三、形式模型

定义共同作用域 $\Sigma$：本轮、正文所指“这一候选”、当前适用的批准条件。给该候选稳定分析标识 $c$，只绑定 E12—E15 与 E20、E22 的原文指代，不伪造候选版本号。动作身份分别为 $a_s$（提交修复与说明）、$a_t$（技术检查）、$a_d$（拟部署）。三者不同，不能由 $a_s$ 或 $a_t$ 推出 $a_d$ 已发生。

部署模型定义：$d$ 为方案要求部署 $c$；$a$ 为该次拟部署具备 ADMIN 本次适用批准；$h$ 为方案采用的故障状态已经正式确认为 P1；$l$ 为方案选择值班负责人启动紧急部署。父边界的必要条件为：

$$F_d=d\Rightarrow\bigl(a\lor(h\land l)\bigr).$$

这里的批准同时绑定本轮、同一候选及部署动作，不能用其他对象、旧轮次、报告接受或质量检查结果替代。自然人身份关系未用于本例违反见证；值班负责人这一明确角色足够表达方案所选执行主体，不需要补造姓名。

词典实际采用 software-ai@0.2.0 的 /frames/18，将部署识别为 CHANGE 类动作；同次查询出现模型部署等候选，但正文未建立模型对象，故不据此改写对象类型。/entities/28 将权限作为 policy 类对象；/roles/13 的管理员仅为候选角色，authoritySemantics 为 candidate_only_policy_evidence_required，不自带业务授权。ADMIN 在本例的批准地位来自 E8。P1 查询未命中，P1/P2 的例外关系直接来自 E8 与正文正式等级，不从未命中推导任何新未知。

DEV、QA 的具体符合性分别比较：已选择的制作交接、独立核对动作是否引入无依据授权、状态升级、版本替换或身份推断，并核对其交付、分工及报告义务的继承。PM 自有职责另以三份子任务是否改派或取消来比较，不要求每个下级替 PM 验收汇报。

## 四、数学计算一

先分别评估正文证据对两条路径的支持，不把证据不足或否定归成任务书新增义务。

普通批准路径的当前支持条件为 $A$。E18 明示没有取得 ADMIN 本次批准：

$$A=0,\qquad A\not=1.$$

因此 K6 对“已有本次 ADMIN 批准支持”给出 VIOLATED，含义是该前置当前明确未满足，而非仅凭无批准就指控某次已发生部署。

$$H=0,\quad Q=1,\qquad (\neg H\land Q)\not\Rightarrow H.$$

## 五、数学计算二

OPS 方案给出的值为：E20 要求部署且选择值班负责人，$d=1,l=1$；E18 与 E21 明示无批准且不补充批准，$a=0$；E21 把实施前等级固定为 P2，$h=0$。这里 $h=0$ 是方案参数，不把将来的实施前状态伪称为已经观测的执行结果。

这就是 K2 的局部违反见证。排期紧不在允许例外中；“值班负责人”满足角色部分也不能替代 P1。OPS 第一段和末段保留批准核对、条件不满足时报停的规则，不能消除中间段的明确相反安排。

## 六、关键区别与可满足性

规则保持：DEV、QA 的具体任务及未重写的父义务可共同成立。OPS 的核对条款也能保留，但其固定部署选择与 E8 不能共同成立；不能用“仍写着批准规则”证明整个方案符合。

文本事实条件：没有 ADMIN 本次批准、正式 P2、没有升级结论是明确否定紧急部署所需条件的依据，不清成未知。技术检查通过与已提交也保持为真。K6、K7 分别检查前置证据支持，不评估发生了部署。

反例与修正见证：保持 $a=0,h=0,l=1$，若把方案改为 $d=0$，则 $F_d=1$，说明父规则本身不强迫发生冲突；而现有方案固定 $d=1$，使 $F_d=0$。另一个满足父条件的设想是 $d=1,a=1$，但这只是公式的可满足见证，不能改写为本例已经获批。令技术质量 $Q$ 在 0 与 1 之间变化，现有 OPS 违反结果均不改变，表明质量不是批准替代变量。

本例没有需要枚举真假补全的明示未知。不得将“未报告现实部署”补成已经部署，也不得据此放行拟议的违规动作。正文的核对要求是核对任务，没有要求 QA 强行写成已批准，因此不存在凭普通确认措辞认定伪造批准的依据。
