## 三、形式模型

设共同轮次为 $\sigma=\mathrm{RT006}$，环境为当前绑定的隔离工作区。三个路径实体分别为 $t=$ `tests/lease/stale-owner.test.mjs`、$d=$ `docs/lease-recovery.md`、$s=$ `src/lease-store.mjs`。它们的身份来自 E9、E14、E15；不以文件名相近推导权限。

定义允许修改集合 $M=\{x\mid x\text{ 是 tests/lease/ 下的测试文件}\}\cup\{d\}$，来源 E9。DEV 明确选择的修改集合为 $D=\{t,d,s\}$。OPS 的动作身份为 `A_OPS_CHECK_PACKAGE`，即在自身隔离目录核对、保留差异和独立执行所交工件；DEV 的修改动作为 `A_DEV_EDIT_OWNER`。二者不是同一动作。QA 的动作身份为 `A_QA_REVIEW`，对象是行为证据、修改清单及授权依据。

工件身份 $H$ 绑定三条路径及“包含生产实现修改”的版本描述（E19）。OPS 的执行安排是 $(\mathrm{OPS},H,\mathrm{isolated},\sigma)$，没有被换成旧实现版本，也没有被解释为现网部署。QA 的核对作用于同一轮清单，检查范围合法性并不预设结果肯定。

采用的 L2 词义为：`code.fix_defect` 是代码变更动作，`release.package` 是创建打包产物动作，`dependency.lock` 涉及锁文件。三个词条分别来自 `software-ai@0.2.0` 的 `/frames/11`、`/frames/16`、`/frames/59`。因此不能把“打包保留修改”自动等同于“实施修改”；词典也不授予修复权限。父文要求沿用已锁定依赖，不转换为新增锁文件任务。

K1—K3 使用同一组局部 PLAN 变量，分别表示各角色任务书是否提出十类具体偏离：$w$ 工作区或现网对象偏离、$f$ 框架或依赖偏离、$o$ 输出目录或归档保护偏离、$r$ 报告要素或真实性分类偏离、$d$ 角色分工偏离、$h$ 路径归因或交付恢复边界偏离、$m$ 未授权范围修改、$c$ 无有效依据改变父条件、$p$ 改派取消 PM 职责、$t$ 冒称跨进程或未运行成功。变量比较的是明确方案要求，未重复的要求按 E11 继承，不比较现实执行是否成功。每个角色均核对其全部正文，不能仅凭岗位名称赋权限。

## 四、数学计算一

先比较修改对象：

$$D\subseteq M\ ?$$

代入具体路径：$t\in M$，$d\in M$，$s\notin M$，故

$$D\setminus M=\{s\}\ne\varnothing.$$

这给出 DEV 的局部违反见证：E15 选择的生产实现文件被 E9 明确排除。不存在用相同数字或不同标签合并对象的问题；此处没有数量换算。此集合论证由 K1 中的 $m=\mathrm{true}$ 承载，并非声称已调用计算器。

对授权支持另设 FACT 变量 $a$：本轮已取得扩大生产代码范围的授权。E16 给出 $a=\mathrm{false}$。READINESS 查询比较条件 $a$ 与当前事实 $\neg a$：

$$\neg a\not\models a.$$

K4 预期为 VIOLATED，含义是该修改前置当前未得到满足，而不是证明某个实际修改已经发生。它不约束此前读契约、整理清单、报告差异或 QA 核对授权的动作。

## 五、数学计算二

定义十类偏离的析取为

$$X=w\lor f\lor o\lor r\lor d\lor h\lor m\lor c\lor p\lor t,$$

父要求投影为 $P=\neg X$。各角色的 child 是其具体安排给出的偏离值合取；这是对方案选择的比较，不把期望的通过结论写入事实。

DEV 的生产修改及无授权状态使 $m=1,c=1$；其余八类未提出偏离，取 0。于是 $X=1$，方案不满足 $P$，K1 预期 VIOLATED。普通继承声明 E17 不能消除这一明确反例。

OPS 的具体动作是自身隔离目录内核对执行、保留完整差异和记录回执；没有提出编辑生产实现、部署到现网、更换框架依赖、覆盖归档、取消报告或改派责任（E18—E20）。十类拟议偏离均为 0，K2 预期 VERIFIED。这里的 $m=0$ 只表示 OPS 没有提出未授权修改，不声称 DEV 的修改合法，也不把 OPS 使用的版本换成未修改版本。

QA 要求逐路径核对授权，保留失败修正记录，向 PM 交付复核报告，并明确最终验收汇总仍由 PM 负责（E21—E23）。它没有要求强行肯定修复有效或已经获批，也没有要求现网扰动；十类拟议偏离均为 0，K3 预期 VERIFIED。

该对照同时检查责任非干涉：DEV 不代批、OPS 只校验执行、QA 向 PM 交付；三者都没有取消 PM 整理计划、验收后汇报的职责。下级无须亲自履行这项 PM 自有职责。

## 六、关键区别与可满足性

规则保持与证据支持分开：OPS、QA 保持适用父规则；DEV 即使声明继承，也因具体生产修改而冲突。当前授权条件不满足由 E16 明确给出，不用“尚无执行日志”推导，也不改成未知。

U1 有两个允许补全：生产缺陷存在，或生产缺陷不存在。两种补全下 E9 的范围排除及另行授权要求均不变，E16 的未授权状态也不变，因此不影响 DEV 的违反见证。它仍影响是否能把问题称为已证实的生产缺陷，必须保留。

反例能说明 OPS 与 DEV 为何不同：OPS 完全可以在自身隔离目录保留越权修改的差异、独立检查并报告“该改动未获授权”，同时不修改生产文件、不触碰现网、不伪报成功。这种安排满足父正文，并不因交接包中存在生产文件就自动成为生产修改。原文没有规定“不得接收或检查含越权修改的工件”，不能补加此禁令。

QA 同样可以报告技术效果有效但范围未获授权，或者技术效果无效且范围未获授权；其任务是核对并分别给依据，没有固定肯定答案。测试成功这一假设也不能推出授权成立。
