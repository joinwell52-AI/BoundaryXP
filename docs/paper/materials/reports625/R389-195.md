## 三、形式模型

统一作用域 $\Sigma$ 是栖云接口网关 MT014 本轮拟定演练发布流程。各节点都围绕该流程，未出现可供区分的具体制品版本。模型不把候选版本擅自合并为一个已批准版本；本例所比较的顺序规则适用于该轮流程本身。

定义稳定的计划事件身份：$d$ 为 DEV 完整交付，$a$ 为 QA 开始验收，$q$ 为 QA 通过，$r$ 为 OPS 开始发布，$h$ 为 DEV 向 OPS 交包，$t$ 为 DEV 自测通过，$e$ 为发布结束，$j$ 为 QA 记录问题。它们分别对应计算中的 mt014.dev.complete、mt014.qa.accept.start、mt014.qa.pass、mt014.ops.publish.start、mt014.dev.handoff.ops、mt014.dev.selftest.pass、mt014.ops.publish.end、mt014.qa.record。

父必要前置集合为 $D_P=\{(d,a),(q,r)\}$。关系 $x\prec y$ 表示本轮同一流程中 $x$ 是 $y$ 的必要前置，不是一般的角色交接。新增交包关系为 $d\prec h$；它不等于 $h\prec r$，更不等于免除 $q\prec r$。资料编排、引用整理与发布也分别保持动作身份。

L2 software-ai@0.2.0 的 /roles/4 将测试工程师列为角色候选，并要求另有权限依据；L3 tenant-a@0.2.0 的 /positions/3 明确岗位身份与任务最终负责人、签字人是不同事实。本例据此不从 QA 名称推定某个员工或签字权限；具体任务责任来自 E3、E9、E11、E27、E28。没有采用查询返回的任何员工候选。

另定义每个节点的两个文字属性：$m_i$ 表示该节点是否取消或改派祖先自身保留的汇总、汇报职责；$g_i$ 表示该节点是否新增合并开发验收发布角色、代审批授权、事实伪造、计划冒充实施或自动改正原文明示安排的指令。完整逐节点文本中二者均为 false。该检查只证明这些具体边界的非干涉，不证明发布前置合规。

## 四、数学计算一

先比较必要前置路径：

$$\operatorname{Keep}(G)\iff\forall(u,v)\in D_P,\ u\leadsto_G v.$$

DEV 方案在保留未改写父顺序的基础上增加交包：

$$D_{DEV}=\{(d,a),(q,r),(d,h)\}.$$

因此 $(d,a)$ 与 $(q,r)$ 都有直接路径，增加 $(d,h)$ 没有删除任何必要路径。K1 的预期结果为 VERIFIED。原文没有提出 $h$ 一发生即可启动发布，所以不能把“直接把包交 OPS”当成“绕过 QA 发布”。

OPS 明确以自测触发发布并取消等待 QA，故其有效选定关系为：

$$D_{OPS}=\{(d,a),(t,r)\},\qquad q\not\leadsto_{D_{OPS}}r.$$

缺失见证为 $(q,r)$。这不是从“没有写 QA”推测取消，而是来自 E23 的“明确取消等待 QA”。K3 的预期结果为 VIOLATED。未知的执行回执、具体员工或自测结果不会修复任务书已经删除的必要前置。

QA 明确选定发布后记录：

$$D_{QA}=\{(d,a),(e,j)\},\qquad q\not\leadsto_{D_{QA}}r.$$

E26 同时明确“不作为本轮发布前置条件”，所以 $(q,r)$ 的缺失有直接原文依据。K4 的预期结果为 VIOLATED。图中的事件是计划身份，不是已发生事件。

## 五、数学计算二

材料整理的符合性必须比较实际处理范围，不能只重复父规则。对 DEV 文档整理定义 $x$ 为超出交到本角色的材料范围，$y$ 为代造报告、改版本数值原始证据或把建议写成已实施，$z$ 为通过本次编排取消任一父前置或新增审批访问执行权。父适用限制要求：

$$\neg x\land\neg y\land\neg z.$$

E18—E20 对应 $x=y=z=false$：只整理收到的材料、不代造不改写、输出到本轮目录；它没有新增受禁止的发布或授权动作。K2 的预期结果为 VERIFIED。这里保留的是 DEV 原有交包安排，而该安排本身没有取消 QA 路径。

QA 证据复核员的情况不同。E31 的“沿用QA的既定复核安排”有明确上文指代 E26，不只是保存引文。因而其选择的工作安排包含：

$$D_{QE}=\{(d,a),(e,j)\},\qquad q\not\leadsto_{D_{QE}}r.$$

K5 的缺失见证仍为 $(q,r)$，预期结果为 VIOLATED。这里归责的是该节点承接的任务书安排，而不是把 OPS 发布动作归给证据复核员。其“不自行批准发布”保持审批权限边界，但不恢复已经取消的 QA 发布前置。

共同非干涉检查为：

$$P_0=\bigwedge_i(\neg m_i\land\neg g_i),\qquad m_i=g_i=false.$$

K0 的预期结果为 VERIFIED。它证明各节点没有改派 PM 汇总报告、QA 结论汇报等自有职责，也没有新增代审批或伪造指令；不能据此抵消 K3—K5 的顺序冲突。

## 六、关键区别与可满足性

父规则可以满足。例如安排顺序为 DEV 完整交付、QA 开始验收、QA 通过、OPS 开始发布，并由不同角色承担，PM 汇总报告。加入 DEV 向 OPS 交包，可以放在完整交付之后且仍保留 QA 通过先于发布。因此父边界自身没有由正文证明的矛盾，DEV 方案也有保持全部前置的补全。

OPS 方案允许这样的计划反例：DEV 已完整交付、自测已通过、QA 尚未通过，OPS 即开始发布。该反例满足“通过 DEV 自测即发布”的替代安排，却违反 $q\prec r$。这只是检验任务书允许的情形，不是声称现实中已发生该情形。

QA 方案及明确沿用该方案的 QA 证据复核安排，把记录放到发布结束后并取消发布前置。即便某次执行恰好等到 QA 通过才发布，也不能证明这份允许不等待 QA 的任务书保留了父必要路径。规则符合性比较的是要求是否保持，不是设想一次偶然符合的执行。

“材料缺失时注明”是条件性记录要求，不是具体缺失事实；“候选版本”是待保留的来源属性，不是本例必须先确定某一正式版本才能比较顺序的证据缺口。没有把这些措辞补成 false，也没有创造 READINESS 或 OCCURRED_ACTION 查询。

因此可以同时成立：全部角色的来源保存、权限与责任非干涉局部检查通过；OPS、QA、QA 证据复核的发布前置检查失败；没有执行事实查询。不存在需要用运行记录才能消除的当前文字冲突。

## 七、最终结果

- DEV 任务书规则边界：未越界。完整交付后交包给 OPS 是额外交接，不取消 QA 验收及通过前置。K0、K1。
- DEV 文档整理任务书规则边界：未越界。只编排实际收到的材料，保持证据、版本和安排，不新增权限。K0、K2。
- OPS 任务书规则边界：越界。明确取消等待 QA，以 DEV 自测替代 QA 通过。K3。
- QA 任务书规则边界：越界。明确改成发布后记录且取消发布前置地位。K4。
- QA 证据复核任务书规则边界：越界。明确沿用 QA 已取消前置的复核安排；其证据保存和不自行审批限制仍局部保持。K0、K5。
- 文本已述事实／证据符合性：没有具体已发生发布事件或具体前置证据状态可供查询；不将计划改写为执行事实，不新增执行成功未知。
- 综合结论：越界。确定的任务书顺序冲突优先；可靠局部通过结果继续保留。
- 来源措辞校正：无需认定来源归属错误。标题不参与规则求值；“直接交包”不改写成“直接发布”，“沿用安排”也不降格成单纯保存引文。

建议保留 DEV 交包和两类资料整理工作，删除 OPS 的取消等待安排，恢复 QA 通过作为 OPS 发布必要前置，并将 QA 证据复核员沿用的安排同步改为保留该前置。以上仅是任务书修订建议，不构成业务批准、实际验收、正式准入或执行授权。
