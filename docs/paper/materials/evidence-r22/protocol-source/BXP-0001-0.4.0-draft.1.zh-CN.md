# BXP-0001：边界分析协议（Boundary Xplain Protocol）

## 摘要

边界分析协议（Boundary Xplain Protocol，BXP）规范任务边界的表达、形式化、确定性求值、身份、交换以及正式发布强制准入。

BXP **不把 7+1 当成协议终点**。7+1 是承载已识别任务语义的标准语义中间表示，用于进入 Formal Boundary Model；协议终点是经过确定性计算得到的 **Boundary Result（边界结果）**。Boundary Result 必须是机器可读、可参照、可交换、可重放、可冻结的数据对象。

对于任何把任务发布到正式规划或执行生命周期中的宿主，BXP 是**强制准入契约**，不是可选检查。草稿任务可以不完整，可以进入分析、澄清和修订；正式任务必须针对当前精确任务版本通过 BXP Admission，否则不得进入下游正式流程。

BXP 的规范处理链为：

```math
\text{Task Semantics}
\rightarrow
IR_{7+1}
\rightarrow
\mathcal{M}(IR)
\rightarrow
\mathcal{B}
\rightarrow
Admission
```

其中：

- $IR_{7+1}$：BXP 标准语义承载层；
- $\mathcal{M}(IR)$：Formal Boundary Model；
- $\mathcal{B}$：确定性 Boundary Result；
- `Admission`：宿主强制执行的正式任务发布准入结果，用于判断当前精确任务版本是否可以进入下游正式生命周期。

BXP 不规定自然语言语义识别必须使用 HanLP、spaCy、其他 NLP、规则、语言模型还是人工审阅。这些属于 Producer 技术。BXP 规范的是：语义如何表示、不确定性如何保留、形式模型如何求值、最终边界如何形成稳定身份并交换，以及正式发布准入如何强制执行。

## 1. 当前地位与规范用语

本文件是仓库内待评审草案，不是 IETF RFC、已采用行业标准、认证计划或发布授权。

英文 MUST / MUST NOT / REQUIRED 对应“必须／不得／必需”，SHOULD / SHOULD NOT 对应“应／不应”，MAY / OPTIONAL 对应“可以／可选”，均为本草案规范要求。

`0.4.0-draft.1` 将 Boundary Result 与正式任务强制准入确立为协议中心。与之匹配的线上 Schema、一致性向量、Operator Profile 与 Host Admission Gate 尚未实现，因此这些资产完成版本化之前，任何实现不得声明符合 `0.4.0-draft.1`。

## 2. 协议目的与数学定义

设已识别任务语义为 $S$。BXP 定义：

```math
S
\xrightarrow{Normalize}
IR_{7+1}
\xrightarrow{Formalize}
\mathcal{M}
\xrightarrow{Evaluate}
\mathcal{B}
```

协议目标不是“抽出八个字段”，而是得到最终的 $\mathcal{B}$：一个可由其他系统验证、冻结、引用、比较和交换的形式任务边界结果，而不需要下游系统反复重新解释原始自然语言。

### 2.1 边界是由约束定义的解空间

设 $\mathcal{X}_{\Sigma}$ 为声明作用域 $\Sigma$ 内所有候选计划、状态或下游实现的全集。Formal Boundary Model 定义有效性谓词：

```math
\chi_{\mathcal{M}}(x)=
Q(x)
\land \neg F(x)
\land K(x)
\land \Phi(x)
```

其中：

- $Q(x)$：要求的结果和义务是否满足；
- $F(x)$：是否触发禁止动作、禁止状态或禁止效果；
- $K(x)$：完成、停止或验收条件是否满足；
- $\Phi(x)$：其他数值、集合、逻辑、时序、排序等形式约束是否满足。

于是，任务允许的解空间为：

```math
\Omega_{\mathcal{B}}
=
\{x\in\mathcal{X}_{\Sigma}\mid \chi_{\mathcal{M}}(x)=true\}
```

Boundary Result 不要求枚举 $\Omega_{\mathcal{B}}$ 的全部成员，但必须包含足够规范的信息，使其他实现能够重构或验证定义这个解空间的边界条件。

如果：

```math
\Omega_{\mathcal{B}}=\varnothing
```

说明当前形式模型不存在可行解，即任务边界 `inconsistent`。

如果：

```math
\Omega_{\mathcal{B}}\neq\varnothing
```

且所有会影响边界的语义、身份、作用域和关系都已确定，则任务才可能形成 `determined` 边界。

### 2.2 边界唯一性不是“7+1 填满”

设 $\mathfrak{I}(S)$ 为同一任务语义下所有有证据支持、协议允许的候选解释集合：

```math
\mathfrak{I}(S)=\{I_1,I_2,\ldots,I_n\}
```

在固定 Operator Profile $O_v$ 下：

```math
\mathfrak{B}(S,O_v)
=
\{Evaluate(\mathcal{M}(I),O_v)\mid I\in\mathfrak{I}(S)\}
```

定义 `CanonBoundary` 去掉展示顺序、说明文字等不改变协议语义的差异，只保留规范边界含义。只有当：

```math
\left|
\{CanonBoundary(b)\mid b\in\mathfrak{B}(S,O_v)\}
\right|=1
```

时，才能认为所有允许解释最终收敛到**同一个规范边界**。

如果两个允许解释得到不同边界，则任务必须保持 `underdetermined`，直到权威澄清消除歧义。

这比“7+1 是否都填了内容”更严格：

```math
AllBucketsNonEmpty
\not\Rightarrow
BoundaryDetermined
```

### 2.3 协议职责分层

BXP 必须严格区分：

1. 自然语言语义识别；
2. 语义标准表达；
3. 形式化；
4. 确定性边界计算；
5. 正式任务准入；
6. 业务裁决或执行授权。

BXP 规范第 2–5 层。第 1 层允许由不同 Producer 实现，第 6 层始终不属于 BXP 权限。

## 3. 第一层：7+1 语义承载层

BXP 的 7+1 标准语义中间表示为：

```math
IR_{7+1}=(I,O,A,P,R,V,C,B)
```

| 标识 | 名称 | 规范含义 |
|---|---|---|
| I | 输入范围 / Input | 任务输入、作用对象、数据、系统、总体及其他明确处于任务范围内的对象。 |
| O | 交付结果 / Output | 明示的交付物或外部可观察结果。 |
| A | 动作 / Actions | 任务中的必需、允许或其他相关动作；已知时必须保留主体、效果、目标及模态。 |
| P | 责任主体与角色分工 / Participants | 参与执行、审批、观察、复核、接收或协作的人、Agent、系统和服务。 |
| R | 资源 / Resources | 数量、预算、容量、截止时间、持续时间及阈值等资源约束。 |
| V | 版本依据 / Version and Provenance | 控制版本、制度、证据来源及时间基线。 |
| C | 完成停止 / Completion | 完成、停止、验收及升级条件。 |
| B | 禁止边界 / Forbidden Boundary | 禁止发生的动作、效果、目标或组合，以及其条件与例外。 |

7+1 是任务语义的标准坐标系，不是最终数学边界：

```math
IR_{7+1}\neq\mathcal{B}
```

符合 BXP 的实现不得把一个已经填充的 7+1 本身描述成最终 Boundary Result。

每个要素必须至少显式保留 `resolved`、`unresolved`、`absent` 三类状态。Producer 的置信度、行业默认值或模型偏好都不得把尚未确定的解释静默改写成确定事实。

## 4. 原文证据与语义身份

每个 `resolved` 或 `unresolved` 的语义声明都必须能够追溯到来源证据。

证据证明“这条语义声明来自哪里”，但证据本身不证明解释已经完整、唯一或正确。

对于候选解释 $I_i$ 与 $I_j$：

```math
CanonBoundary(\mathcal{B}(I_i))
\neq
CanonBoundary(\mathcal{B}(I_j))
\Rightarrow
State=underdetermined
```

直到通过新证据、澄清或协议外的明确权威选择消除这种边界差异。

## 5. 第二层：Formal Boundary Model

7+1 语义 IR 在进入确定性边界计算前，必须转换为形式边界模型。

BXP 定义抽象模型：

```math
\mathcal{M}(IR)=
(E,\Sigma,Q,F,K,\mathcal{R},D,\Phi)
```

其中：

- $E$：已经确定身份的实体与制品；
- $\Sigma$：显式作用域与状态切片；
- $Q$：必须满足的结果与义务；
- $F$：禁止动作、禁止对象、禁止效果或禁止状态组合；
- $K$：完成与停止条件；
- $\mathcal{R}$：参与者、角色与关系事实；
- $D$：依赖、交接、来源与版本关系；
- $\Phi$：数值、集合、逻辑、时序、排序等形式约束。

上述元组是协议抽象模型。线上格式可以用多个类型化集合表达，不要求字面上保存为一个元组。

例如：

```math
\text{耗时不得超过 10 分钟}
\Rightarrow
duration\le600s
```

```math
\text{未经 ADMIN 批准不得发布}
\Rightarrow
\neg approved_{ADMIN}\Rightarrow\neg publish
```

```math
\text{不得修改生产数据库}
\Rightarrow
ModifiedTargets\cap ProductionDatabase=\varnothing
```

形式化不得补造 7+1 IR 中不存在的事实。身份、单位、作用域、关系或适用性尚未确定时，形式模型必须保留这种不确定状态，而不是为了“能算”而制造一个值。

## 6. 第三层：边界求值

边界求值使用版本化 Operator Profile $O_v$ 对形式模型进行计算：

```math
\mathcal{B}=Evaluate(\mathcal{M},O_v)
```

对于完全相同的 $\mathcal{M}$ 和完全相同的 $O_v$，计算器必须产生完全相同的 $\mathcal{B}$：

```math
\mathcal{M}_1=\mathcal{M}_2
\land
O_{v1}=O_{v2}
\Rightarrow
Evaluate(\mathcal{M}_1,O_{v1})
=
Evaluate(\mathcal{M}_2,O_{v2})
```

边界计算不得依赖随机采样、当前时钟、模型 temperature、网络实时返回或其他未声明外部状态。

### 6.1 计算算子是方法，不是协议核心

BXP 可以定义或注册多种确定性计算算子，包括区间代数、类型集合、交接与数据流、依赖图、命题逻辑、时间、排序、基数、身份等价、可达性、资源以及版本来源核验。

任何一种具体算法都不构成 BXP 本身的定义。计算算子只是对 Formal Boundary Model 求值的版本化方法。

每种算子都必须具有确定语义、有限输入规则、明确的 unresolved 行为和机器可验证输出。

## 7. 第四层：Boundary Result

Boundary Result 是 BXP 的最终协议数据对象。

Boundary Result 必须回答两个问题：

1. **这个任务的边界是否已经确定？**
2. **如果已经确定，确定后的边界是什么？**

抽象结果表示为：

```math
\mathcal{B}=
(State,
Required,
Forbidden,
Limits,
Completion,
Relations,
Dependencies,
Provenance,
Findings)
```

线上 Schema 可以采用不同字段组织方式，但必须保留这些语义以及确定性结果身份。

### 7.1 Boundary State

Boundary Result 必须暴露以下状态之一，或版本化的等价表示：

- `determined`：当前 Profile 要求的所有边界相关语义与身份已经确定，形式模型有效，规范边界唯一，要求的计算结果确定且不存在冲突；
- `underdetermined`：仍存在可能改变 Boundary Result 的语义、身份、作用域、单位、适用性或其他未确定信息；
- `inconsistent`：模型已经足够明确，并且可以证明提交的要求不能同时成立；
- `invalid`：提交的协议数据在结构或语义上无效，无法产生合法边界。

仅仅“程序已经算完”不得被标记为 `determined`。

一个抽象确定条件为：

```math
Determined(\mathcal{B})=
Valid
\land RequiredResolved
\land IdentityResolved
\land ScopeResolved
\land UniqueCanonicalBoundary
\land Consistent
```

其中：

```math
UniqueCanonicalBoundary
\iff
\left|
\{CanonBoundary(b)\mid b\in\mathfrak{B}(S,O_v)\}
\right|=1
```

Profile 可以进一步收紧这一条件，但不得削弱不确定性保留原则。

### 7.2 准确性的含义

BXP 所说的准确，不是“模型置信度很高”，而是：对已经提交的形式模型进行精确、确定性计算，并且不把已知不确定性伪装成确定结果。

```math
Ambiguous
\not\Rightarrow
ChooseMostLikely
```

而必须：

```math
Ambiguous
\Rightarrow
underdetermined
```

BXP 不声称某个 Parser 或 NLP Producer 永远正确理解自然语言。抽取质量需要独立评测与符合性证据。但 BXP 要求已知不确定性不得被伪装为确定边界。

## 8. 正式任务强制准入契约

BXP 是正式任务发布的强制准入契约。

宿主可以允许不完整、冲突或未确定的草稿存在于起草、分析、澄清、修订状态；但在准入成功之前，宿主**不得**把该任务发布到正式规划或执行生命周期。

定义正式发布准入谓词：

```math
Admit(T_v)=
ProtocolValid(T_v)
\land BoundaryDetermined(T_v)
\land ReleaseConditions(T_v)
\land VersionBound(T_v)
```

只有当：

```math
Admit(T_v)=true
```

宿主才可以发布正式任务进入下游流程。

如果：

```math
Admit(T_v)=false
```

或者准入结果无法计算，宿主必须 **fail closed**，不得发布任务。

### 8.1 准入绝不等于“7+1 填满”

```math
AllBucketsNonEmpty
\not\Rightarrow
Admit(T_v)
```

同样：

```math
Completeness=complete
\not\Rightarrow
Admit(T_v)
```

准入必须满足完整协议判据，包括形式模型有效、Boundary Result 已确定、没有边界相关歧义、没有冲突、满足 Profile 发布条件，并且绑定当前精确任务版本。

### 8.2 草稿与正式任务必须分开

草稿不完善不是协议失败。草稿可以处于 `underdetermined`、`inconsistent` 或其他未完成状态，用于分析、修改和澄清。

正式发布不同。任何被标记为或被系统当作正式任务的对象，都必须先通过 BXP Admission。

宿主不得用页面提示、警告、“我已知晓”按钮、可跳过检查按钮、模型建议或人工口头确认替代强制门禁。

### 8.3 ADMIN 修改任务后旧准入立即失效

设 $D_S(T_v)$ 为已准入任务版本的精确来源身份。如果 ADMIN 或其他权威来源修改任务，使：

```math
D_S(T_{v+1})\neq D_S(T_v)
```

则：

```math
Admission(T_v)
\not\Rightarrow
Admission(T_{v+1})
```

旧准入必须被视为 `stale`。即使新任务随后碰巧计算得到相同 Boundary Result，也必须重新执行协议校验、必要形式化、边界求值和正式准入。

### 8.4 正式发布绑定

正式发布应形成可验证的 Admission Identity：

```math
D_A=
Hash(
ProtocolVersion,
Profile,
D_S,
D_{IR},
D_M,
O_v,
D_B
)
```

宿主在正式发布时必须重新核对当前绑定。如果：

```math
D_A^{current}\neq D_A^{admitted}
\Rightarrow
Release=blocked
```

则不得继续发布。

### 8.5 宿主必须负责强制拦截

职责边界为：

- 模型或其他 Producer 负责提出候选语义；
- BXP 负责验证、形式化、计算并形成 Boundary Result 与 Admission 状态；
- Host 负责强制执行准入门禁。

任何模型输出、页面按钮、提示语、缓存结果或操作人员声明，都不得绕过失败、过期或不匹配的 BXP Admission。

### 8.6 准入不等于执行授权

```math
Admission\neq ExecutionAuthorization
```

BXP Admission 只表示任务在所声明 BXP Profile 下满足进入正式下游生命周期的结构与数学边界条件。业务审批、执行者授权、凭据、运行时安全检查以及真实执行权限，仍然由各自系统负责。

## 9. 可参照、可交换、可冻结、可重放

Boundary Result 是稳定数据对象，不是文字建议。

符合 BXP 的结果模型至少应绑定：

```math
D_S=Hash(Source)
```

```math
D_{IR}=Hash(IR_{7+1}+FormalizationInputs)
```

```math
D_M=Hash(Canonical(\mathcal{M}))
```

```math
D_B=Hash(Canonical(\mathcal{B}))
```

任何会改变确定性 Boundary Result 的变化，都必须改变 $D_B$。

稳定边界引用可以表示为：

```math
Ref_{\mathcal{B}}=
(ProtocolVersion,Profile,O_v,D_B)
```

**可参照（referenceable）**：下游系统可以凭该引用绑定这一边界，而不必重新解释自然语言。

**可交换（exchangeable）**：其他实现可以验证 Schema、协议版本、Operator Profile 与摘要，不要求使用相同 NLP 引擎或相同 Producer。

**可冻结（freezable）**：精确输入、Operator Profile 与最终边界身份被固定，之后来源、IR、形式化或算子变化都不得静默改变已引用边界。

**可重放（replayable）**：独立符合实现能够重新计算：

```math
Evaluate(\mathcal{M},O_v)=\mathcal{B}
```

并得到相同规范结果身份。

## 10. Producer 独立性

BXP 不规定某一种自然语言语义识别引擎。Producer 可以使用 HanLP、spaCy、其他 NLP、确定性规则、统计模型、神经网络、LLM、人工标注或这些方法的组合。

Producer 的选择不得改变 I/O/A/P/R/V/C/B 的协议含义，也不得改变 Boundary Result 的形式语义。

如果两个 Producer 的输出语义等价：

```math
IR_a\equiv IR_b
\land
\mathcal{M}(IR_a)=\mathcal{M}(IR_b)
\Rightarrow
\mathcal{B}_a=\mathcal{B}_b
```

那么在相同 Operator Profile 下必须得到相同 Boundary Result。

## 11. 下游符合性比较

一个已经准入的 Boundary Result 可以作为后续计划、拆分任务和实现方案的基准。

对于下游对象 $X$：

```math
Conform(X,\mathcal{B})
\iff
X\in\Omega_{\mathcal{B}}
```

等价地：

```math
X\models\chi_{\mathcal{M}}
```

典型诊断可以进一步分解为：

```math
Missing=
Required_{\mathcal{B}}
\setminus
Covered_X
```

```math
Violation=
Actions_X
\cap
Forbidden_{\mathcal{B}}
```

```math
ConstraintViolation=
\{\phi\in\Phi_{\mathcal{B}}\mid X\not\models\phi\}
```

因此 PM 的方案、子任务或其他下游对象是否偏离原始任务，可以对已冻结 Boundary Result 做形式化符合性比较，而不是依赖“模型感觉对不对”。

BXP 不要求下游消费者必须是 PM、Agent、工作流系统或人工团队。BXP 标准化的是这些消费者共同引用的边界数据。

## 12. 当前计算算子家族

现有 BXP 实现历史已经使用若干确定性算子。它们仍然有用，但只是当前求值方法，不是 BXP 的定义本身。

### 12.1 Profile 完备性

```math
Deficit=
Required(profile)
\setminus
Resolved(IR)
```

### 12.2 区间求交

```math
L=\max_i L_i,
\qquad
U=\min_i U_i
```

### 12.3 类型集合交集

```math
Overlap=
RequestedTargets
\cap
ForbiddenTargets
```

### 12.4 交接缺口

```math
Available=
DeclaredOutputs
\cup
ExternalInputs
```

```math
Missing=
RequiredInputs
\setminus
Available
```

### 12.5 依赖一致性

强制前置关系的有向图存在环时，该关系不一致。

### 12.6 命题一致性

在一个已确定作用域中，全部提交公式与假设合取求值；存在至少一个赋值时为 satisfiable，否则为 unsatisfiable。

这些算子可以在版本化 Operator Profile 下独立演进，只要协议确定性与 Boundary Result 语义保持不变。

## 13. 权限边界

Boundary Result 描述的是经过计算的任务边界事实。它本身不作业务裁决、不授予权限、不授权执行、不证明合法性、不证明安全，也不证明任务已经完成。

任何暴露权限字段的 BXP 线上结果都必须保留等价于：

```json
{
  "business_decision": null,
  "execution_authorization": null
}
```

任何 BXP 符合性等级都不得把 `determined` 的 Boundary Result 或成功 Admission 重新定义为执行授权。

## 14. 版本与迁移

草案版本采用 `MAJOR.MINOR.PATCH-draft.N`。

`0.4.0-draft.1` 把 BXP 的协议中心从“7+1 + 固定几种计算方法”调整为：

```math
\boxed{
\text{Task Semantics}
\rightarrow
IR_{7+1}
\rightarrow
FormalBoundaryModel
\rightarrow
BoundaryResult
\rightarrow
Admission
}
```

本草案明确**不声称**当前 `boundx-task/v1`、`boundx-result/v1`、既有冻结向量或当前产品 Host 已经实现全部新的 Boundary Result 与强制 Admission 要求。

后续实施任务必须对受影响的 Schema、Operator Profile、一致性套件、正式发布记录与 Host Gate 进行版本化，之后才能声明 `0.4.0-draft.1` 已实现。

既有 `0.3.0-draft.2` 行为仍然只是历史实现证据，不得重新贴标签声称符合 `0.4.0-draft.1`。

## 15. BXP 核心定义

BXP 的稳定核心不是 7+1 本身，也不是某一种计算算法。

```math
\boxed{
IR_{7+1}
\rightarrow
\mathcal{M}(IR)
\rightarrow
\mathcal{B}
\rightarrow
Admission
}
```

BXP 使用标准语义承载层建立形式任务边界模型，通过确定性计算形成 Boundary Result，并要求正式任务发布必须绑定并通过这一精确结果的准入。

7+1 是为了形式化。

形式化是为了确定性计算。

确定性计算是为了产生 Boundary Result。

Boundary Result 是为了形成准确、可参照、可交换、可冻结、可重放的任务边界基线。

Admission 是为了确保任何正式任务进入后续流程之前，都必须满足这一边界契约。
