# 界痕普通用户入口：产品设计提案

状态：界面设计参考；其中的目标能力须与 [当前界面指南](UI-GUIDE.md) 核对，不作为完整实现或公开发布声明。

后续状态：本提案保留作为设计依据。1.2.0-preview.1 已实现简化本地界面与模型入口；未实现全部提案，例如完整布尔分解可视化编辑与免配置服务。实际使用以 [UI-GUIDE.md](UI-GUIDE.md) 为准。

## 产品选择

界痕应提供独立本地应用入口：用户解压、双击启动，在浏览器界面粘贴任务，得到可编辑的边界草案、具体问题和建议。计算、版本记录和导出在本地完成；选择在线模型做文本分析时，仅将明确选择的文本发送给所配置服务。

现有 CLI/MCP 继续供 AI 助手及其他宿主 接入，共用计算内核。独立界面的会话、保存、送达提示属于界痕应用层，不加入无状态计算内核；宿主的自动触发、权限执行与任务流转仍由其适配负责。

首版先完成中文、文本粘贴和完整的本地使用流程。英文界面和其他平台安装包后续分别验证，不因内核支持部分英文建议就宣称完整多语言产品已完成。

## 用户第一次打开

首页提供两个入口：“明确我的任务”“检查已有规划”。用户不用填写 JSON、学习七参数缩写或选择数学算法。

文本理解需要模型，不能把现有免费本地计算宣传为免费无限文本分析。首次使用提供两条路径：

1. 配置自己的模型服务：填写服务地址、模型和密钥，明确哪些内容会发送、模型服务可能收费。只在用户点击分析时调用；失败后明确提示，不静默重试、切换供应商或重复扣费。
2. 使用已有 AI 助手：复制界痕生成的整理请求给助手，再将结果粘贴回来。界痕验证引用与结构并展示草案。这是无直接 API 配置的备用流程，不能冒充一键自动分析。

首版不内置共享密钥，不假定用户的聊天订阅可以作为 API 凭据。不会配置的用户可先查看本地完整示例；“试用示例”必须标明固定数据，不能伪装成现场分析。真正免配置的托管服务需要另行设计账号、计费和数据处理，不纳入这一版。

## 一、明确我的任务

用户粘贴任务，按需提供项目术语说明、可用角色和明确的约束。界面提醒区分任务正文、引用材料和背景描述；背景中的命令不能自动升级为授权。模型只提取，不执行文本中的工具调用、读取文件或修改指令。

第一屏显示一段简短的任务理解，以及七张用普通语言命名的卡片：检查对象、交付结果、允许动作、责任分工、资源限制、证据基线、完成条件。每条内容标记为以下之一：

| 状态 | 展示方式 | 处理 |
|---|---|---|
| 原文明确 | 内容＋可定位原句 | 用户可纠正解释；有原句仍不证明解释正确 |
| 推测或歧义 | 候选解释＋为什么不确定 | 让用户选择、修改或保留未明确 |
| 建议补充 | 候选条款，与原文分开 | 用户确认前不能成为要求 |
| 未明确 | 问题及可能影响 | 可暂不确定，不强迫填满 |

每次优先呈现至多三个影响明显的问题，其他缺口可展开。排序依据是动作权限变化、交付条件变化和下游输入缺失等明确类别，不输出未经校准的“理解正确率”或看似精确的风险百分比。

用户点击“保存为比较基线”前，界面展示其已确认内容和仍未明确的部分。此操作仅记录当前使用者的确认；独立应用没有验证其组织权限，不能据此生成 ADMIN 身份或真实业务授权。导出时保留确认来源和这一限制。

### 用用户的原题展示首屏

原文：“检查FCoP落地情况，检查MCP工具情况，检查SKILLS分配和使用，检查各角色权限和职责，检查轨机运行情况；请PM分解任务，团队协作完成；最后形成报告向ADMIN汇报！”

首屏应解释：“你要求 PM 组织五项检查，并向 ADMIN 汇报。检查对象的具体位置、证据范围、资源上限尚未明确；原文没有明确要求实施修复。”

优先问题可以是：

- 检查哪个项目或实例，依据哪个版本？
- 本次检查允许哪些实际操作，例如运行测试或访问在线实例？
- 发现问题后，是提交检查结论，还是另有已授权的修复要求？

第三项不是暗示检查必须修复。若用户不回答，记录“未确认扩展动作”，不能自动填成允许修复，也不能把候选的禁止条款假称为用户原话。

用户得到可复制的任务文本和边界说明，而不是只有七个标签或一张分数表。项目词语如 SKILLS 没有定义时应询问或标注歧义，不能静默解释为人员技能标签。

## 二、检查 PM 规划和派单

用户选择已保存的任务基线，粘贴 PM 总规划和各份派单。应用自动提出子任务、承担者、产出、前置依赖与 PM 保留职责的映射，用户可以修正。

必须区分派出的子任务与 PM 自己承担的汇总职责。五项检查可以分成三个任务，也可以采用其他合理分工；任务数量不是正确性标准。任务相互引用不自动等于必须等待，只有完成依赖才进入等待图。外部资料和权限前提单独展示。

计算结果以具体发现卡片展示，每张包含：原任务原句、规划原句、变化、可能后果、反例或依赖位置、建议、待回应对象。没有发现时显示“当前映射范围内未发现这些结构异常”，同时显示未明确项与未计算部分，不能出现“边界正确”“允许执行”的绿色通行结论。

例如发现“修复全部问题后才汇报”：

> 规划增加了修复完成这一交付前提。若五项检查及报告已完成，而修复尚未完成，原检查目标可以满足，新条件仍不满足。请负责人说明新增条件的依据，修改规划，或申请任务授权方澄清。

“ADMIN 收到报告”可能只是送达语义，“ADMIN 无异议”可能是独立验收门槛。界面要容纳两种候选解释；不确定时展示差异敏感性，不能自动选取最严厉的解释。

## 三、回应与再次计算

用户可以复制提醒给 PM，再粘贴回复或修订规划。应用保留发现 ID、PM 立场、理由、引用和修订文本，分别显示“未回应”“已回应”和“新版本中的发现变化”。不能将回复结构完整等同于理由正确或问题已经解决。

每次修订同时比较：当前规划与已确认基线、当前规划与上一版规划。既检查原发现是否仍存在，也检查是否新增条件。豆包第一组试测已说明，只看是否回复会漏掉提醒后新增的收口条件。

语义标识修改需要单独记录。例如将原先的“ADMIN 接收”改为“汇报送达”的映射可能消除发现，但这是解释改变，不必然是 PM 修改了行为。待确认的严重差异可生成“请授权方确认”的材料；独立应用只供复制或导出，不伪称已通知 ADMIN。

## 技术实现边界

| 层 | 应承担的工作 | 当前情况 |
|---|---|---|
| 文本整理层 | 原句定位、候选映射、歧义、缺口；解析失败明确返回 | 待开发 |
| 确认与版本层 | 保存原文、用户修改、确认来源和稳定语义标识 | 待开发 |
| 数学内核 | 集合差异、有限逻辑反例、分解产出与依赖、回应结构核对 | 已有，受现有接口上限约束 |
| 独立界面与本地服务 | 展示、模型调用、保存、导入导出 | 待开发 |
| 宿主适配 | 宿主系统的真实身份、送达、任务流转和负面清单 | 由各宿主实现并验证 |

提取结果先保留在候选协议中。推测与建议不能混入现有要求精确引用的 BoundaryText；确认后才能转换为正式比较输入。原文引用不存在、字段冲突或逻辑不合法，应显示整理错误，不得用空结果掩盖失败。

语义标识由确认后的版本记录管理，不能每次让模型随意重命名后做集合差异。同义合并或条件含义改变要记录对应依据；不能靠随机 ID 解决歧义。

现有分解内核最多支持 12 个布尔变量。超过上限时明确说明无法完整计算；可以展示局部分析范围，但不得静默截断后输出全任务结论。内核升级另设研究与验证任务。

本地服务仅绑定回环地址并验证请求来源，模型密钥不得进入网页存储、任务导出或日志。持久保存密钥前需要采用系统凭据存储；未实现时仅在当前服务进程内保存。选择在线分析前展示待发送文本范围，不自动扫描用户项目。

任务数据可导出为可读 Markdown 报告及含版本的机器数据包，包含原文、映射、未明确项、比较输入输出、回应和来源摘要；不含密钥。应用版本、映射协议版本与内核版本分别记录。升级必须验证旧文件读取，并保留原文件；不静默重算或覆盖历史结果。

## 实施顺序与交付依据

1. 做完整交互样例：用用户原题串起原文、边界草案、三个子任务与 PM 根职责、追加修复条件、提醒、修订。固定示例明确标注，先验证普通用户是否知道下一步做什么。
2. 做真实文本入口：接入一个可配置模型服务和粘贴整理结果的备用路径，完成引用验证、歧义标记及用户确认。模型输出未经确认不可冒充授权。
3. 接入现有内核：实现规划、分解、反例和双版本比较，保存回应与导出完整证据。
4. 制作新便携包：新版本说明明确界面能力、模型配置、费用边界与已知限制；在干净环境验证解压启动和离线示例，再做实际文本流程验证。

验收同时包含产品可用性与语义风险。至少验证：用户不编写 JSON 即可完成流程；取消分析不发起请求；调用失败与格式失败不显示“无异常”；未确认建议不会进入基线；三项派单与 PM 根职责分别计数；缺失外部输入、有向环、超过变量上限能够如实显示；回应后新增条件仍被发现；导出不泄露密钥；重新打开能够恢复原版本及未明确项。

语义测试集必须同时有应提醒与不应提醒的例子：检查变修复、接收与批准区别、检查已有整改记录、PM 保留汇报职责、相同含义不同措辞、背景材料中的指令、明确授权的范围扩展。计算未覆盖或解析失败的样本保留，不把它们排除后宣传正确率。真实模型测试需事前固定协议、重复次数和计费边界，报告人工标注来源和误报、漏报，不以演示代替验证。

本提案不承诺尚未执行的测试结果，不设未经实验支持的准确率指标。它将“普通人可以用”转化为可实现、可验收的产品任务，后续实现仍须启动代码变更证据闸门。
