## 结论

这不是标准文本太复杂、缺少业务执行观测或用户输入错误导致的。当前实现有分项求解器，但没有把MANUAL-TEST-001.md第九节定义的抽象联合约束及见证建立起来。执行观测用于判定任务是否实际完成；静态可满足性可以搜索数学赋值，不需要先实际执行任务。此前把两者混在“未知”说明中是不充分的。

## 1. 联合结果根本没有计算

安装源码research/7plus1-parser/llm-first-028/calculation-results.mjs第88行直接返回joint_cross_domain_execution_feasibility:'NOT_PROVEN'。不是某次联合求解失败后的返回。calculus.mjs第191行求布尔分量、第195行交区间、第199行检测依赖环，第200行汇集冲突列表；没有联合变量、联合约束、联合见证或见证逐约束核验。

这意味着即便所有分项都成功，该代码路径也无法输出标准中的F非空及完整联合满足见证。把此字段改为PROVEN同样不会补上计算。

## 2. 动作与状态存在未建模的连接

calculus.mjs第70行按['STATE',predicate,event_id,args]构造状态变量，第97/139行按['EVENT_EXECUTED',event_id]构造动作变量。二者ID不同，没有显式状态阶段/结果语义的连接约束。

机器复核发现：保存的布尔见证使交付事件deliver=true、其明确引用的“已交付(summary,admin)”状态=false、任务完成=false；与此同时当前23条布尔公式全部通过Core.evaluateBooleanAssignment核验。该见证满足当前较弱的模型，但不能作为标准所要求的完成路径联合见证。

不能粗暴写所有EVENT↔STATE：例如“复核发生”不等于“复核通过”，停止动作和停止期间也有状态转换差异。根因是合同/IR及消费端没有明确表达并消费动作阶段、结果状态和生命周期关系，求解器因此缺少可以合法加入的桥接约束。

## 3. 查询目标没有区别

calculus.mjs只求当前公式集合的任意满足赋值，没有显式请求“完成状态成立的路径”或“高危停止分支”等查询。一个C=false的模型可能满足C↔K，并不证明存在C=true的完成路径。

标准文档分别要求公式解空间与给定完成路径见证。求解目标必须单独记录，不能将任意SAT冒称成功完成可达性，也不能通过把所有触发状态固定false来证明每个分支可行。

## 4. 产物、区间与时序尚未参与联合约束

calculus.mjs第182行只对产物依赖调用evaluateArtifactAvailability；artifacts.mjs第25—28行没有实际观测则返回UNKNOWN。该运行7条可用性关系全部UNKNOWN，没有建立静态可用性变量和生产—使用约束进入联合搜索。没有观测不妨碍抽象数学搜索，但当前只有观测核验接口。

时间区间、依赖图又分别计算，不输出统一的抽象时间赋值与约束验证。标准不要求实际工期预测，也不能凭空填写各事件耗时；所缺的是已有明确先后、可用性和总期限之间可核验的联合抽象见证。

## 5. 操作比较只支持对象不相交或名称完全相等

calculation-results.mjs第59—71行：对象相交后，只有left.operation===right.operation才继续比较主体、条件和作用域。Schema中的event.predicate只是字符串，没有可消费的操作关系/效果语义。因此当前四项待定为组织与修改、两项检查与修改、停止与继续。

这些待定不是四个已证明冲突，也不自动证明整体无解。对所有交叉操作做相容性证明，与搜索一个符合显式抽象约束的见证是不同问题。联合模型须明确自己的抽象操作关系和证明范围；不能用名称不同推相容，也不能把每一对未证明关系笼统当成业务不可能。
