## LLM与程序分别得到什么

LLM最终IR有113个语义节点。两份读取对象为同一任务内的TASK_FIXED变量，域均是{x,y,z}；两个读取动作是无条件义务；身份不同为独立约束。任何主体实际读取y或z均受禁止，三项要求没有被删减或改成原文歧义。

独立审阅给出113项SUPPORT，没有omission，同时明确保留“仅依据DEV自己读取的文件”的排他性表达缺口。技术校验通过、错误0，113个节点被技术接受；这不等于逐原文语义和最终7+1已经完整。

生产程序得到：`result=UNSAT`，`analysis_scope=NECESSARY_CONSTRAINT_CONFLICT`，必要约束子问题含23条要求，后端等级BACKEND_RESULT。冲突Core为两个对象变量域、`r_distinct`及`r_read_ban`。两个必须读取动作的实例化来自原文无条件义务，不把所有现实事件域关闭为节点清单。

它对应人工推导：

```text
U={x,y,z}，R⊆U，|R|=2，R∩{y,z}=∅。
所以R⊆{x}，|R|≤1，与|R|=2矛盾。
Ω_read=∅；任何保留这些必要约束的完整模型均无解。
```

程序冲突Core的断言数量与人工C1/C2/C3数量不同：C1被分成两个对象变量域，C2同时含必需读取实例及身份不同；不能仅按断言个数判错，也不宣称后端已经求出完整任务的全局最小核。

## 剩余问题准确归因

1. **合同表达能力**：只依据已读文件的排他性，当前BASIS正向角色与DATA_USE不能封闭全部实际依据。解析和审阅都承认，程序不能从note／原文扫描补答案。
2. **LLM接口标注＋消费者**：规范与版本在原IR中真实存在，但LLM没有任何requirement标V；消费者只投影requirement.views，遗漏task上下文中的该依据，并把空槽中文写成“没有明示要求”。审阅113项SUPPORT没拦住该最终视图遗漏。这不是读取矛盾求解算错，也不是原文缺规范。
3. **有限查询支持**：环境和全外部输入政策未进入本次必要子问题；完整开放域查询仍NOT_RUN。没有完整执行域／查询角色取值时，不把Unknown当空集合或自动许可。已证明必要矛盾仍足以判无解，不能因此说其余字段已经完整验收。
