## 3. LLM、资源合同、审阅和程序分别有什么问题

### 3.1 收件参数错位：生成错误，合同说明不够，校验和审阅漏检

原文要求ADMIN完整收到两份报告。实际是：

```text
received_dev_report = RECEIVED_COMPLETE(dev_report, admin, deliver)
received_ops_report = RECEIVED_COMPLETE(ops_report, admin, deliver)
```

同版`evaluate.mjs`、`compile.mjs`和`verify-model.mjs`一致把第一个对象解释为receiver，第二个对象解释为artifact。因此候选结构实际解释成“报告作为接收者收到ADMIN”。

这不是节点ID与标准不同，也不是展示文案问题。两个参数类型都是OBJECT，只有类型检查不能发现错绑定。实际模型可见注册表只给出`OBJECT,OBJECT,EVENT? -> BOOLEAN`，SEMANTICS没有把这两个对象的位置语义说明完整。这是模型输出错误与合同接口说明缺陷共同作用；不能全部归因于模型能力。

### 3.2 诊断封闭范围和资源占用：合同/实现的表达缺口

最终IR自己保留了`diagnosis_closed_domain_gap`和`slot_binding_gap`，第一轮审阅也明确指出。它没有把缺口伪装成成功，这一点正确；但功能确实未完成。

修复应提供通用的动作类别/模板归属和资源占用接口，使“所有同类实例仅限指定范围”与“事件在自身区间占用同一资源”可计算。不能写008专用诊断规则、按句子补字段，或简单禁止所有OTHER动作。

### 3.3 同版合同未实际交付：宿主资源适配错误

`direct-ir-kernel-resources.mjs`把Skill版本字符串从1.4替换为2.0，但仍保留Skill对`contracts/candidate-ir-v1/CONTRACT.md`的要求；实际资源给的是`docs/ir-kernel/SEMANTICS.md`、注册表与Schema，没有交付所指同版完整合同。

第一轮审阅已有RESOURCE_CONTRACT_MISMATCH。补丁仍被启动，第二轮审阅明确因同一原因停止逐节点语义审阅，返回：

```text
reviews=[]
omissions=[]
issues=[RESOURCE_CONTRACT_MISMATCH]
```

第一轮112条SUPPORT被最终空审阅结果替换，最后124个节点均未获得本轮审阅支持。空omissions不是没有遗漏。程序仍将修订事务记为`APPLIED_AND_REVIEWED`，这一名字没有准确区分“收到了合法审阅JSON”和“实际完成语义审阅”。

这是资源交付和审阅状态处理问题，**不是任务原文缺陷**。应在启动模型前验证完整资源合同，审阅资源阻断时保存失败状态，不把空审阅当作完成。

### 3.4 P/R槽位归属不正确，程序直接沿用了候选归槽

原协议P是责任主体与角色分工，R是资源及量化限制。本次DEV时长、OPS时长、执行合计与整体耗时要求的`views`却都是P；动作义务使用A/R。程序投影直接使用这些views，所以最终P/R错位。

当前提供的2.0 SEMANTICS没有完整带上原1.4合同中的7+1维度定义。必须把定义放进唯一同版合同，并对有确定结构依据的维度矛盾做技术检查；不能让程序扫描原文重猜语义。

### 3.5 全约束查询没有匹配开放域：程序查询接线/支持缺口

界面默认要求全约束SAT，而生成IR中环境与禁止边界使用开放`TASK_EVENTS(task)`。当前有限域求解器要求显式、完整的查询计划快照才能枚举任务事件；本次没有这样的查询输入，于是报`OPEN_EVENT_DOMAIN`，全案Z3求解没有启动。

**不得为消除报错而把已生成7个事件直接宣称成所有允许事件。** 原文没有禁止组织或交付动作，F02只封闭诊断类。生成图中的节点清单也不是未来事件的完整观测。

下一步应明确区分开放规则表达、有限计划查询和可独立求解子问题。完整边界结果仍须保留未覆盖规则，局部结果注明范围；若要全域证明，则需要相应支持而非把未决删掉。

### 3.6 正常未陈述信息被统一计为缺口

报告生成完成时点已补回，`report_generation_time_gap`已经改为UNSPECIFIED，仅说明原文未给生成开始/时长/执行者。但normalize仍把所有issues统一写为DECLARED_SEMANTIC_ISSUE。这会把正常未陈述字段与明示含义无法表达混为一类，需要按issue种类和影响范围区分。不能为消除缺口而补造零时长或执行者。
