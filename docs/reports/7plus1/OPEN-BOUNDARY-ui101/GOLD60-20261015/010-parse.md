### 附录必须保留的内容关系

**A.1 的六项价值及适用判断：**

- 可追踪：任务、报告、问题形成文件，供后来者复盘。
- 可分工：ADMIN 对接 leader（如 PLANNER），无需直接管理每个执行角色。
- 可审计：任务编写、交付及误动他人职责有证据。
- 可中断恢复：换模型、会话或隔天继续，不依赖聊天记忆。
- 减少口头扯皮：未写 TASK 不算正式任务，未写 REPORT 不算完成。
- 防止 Agent 自作主张：角色、线程、任务边界通过文件确认。  
  来源：第一段“具体价值”六项清单。

价值的机制是从“聊天里的临时默契”转为“文件系统上的可追溯协议”，让 ADMIN 不必持续记住派单、进度和越界状态。适用于多人、多 Agent、需要审计的工作，尤其涉及长线程、角色切换和责任审计；不宜成为所有随手操作的默认流程。代价包括小任务流程过重、`task → do → report → archive` 的流程成本，以及工具或角色绑定状态处理不当可能引起“历史角色警告”。  
来源：“这些状态都落在文件里”“适合‘多人/多 Agent/需要审计’的工作”“不适合当成所有随手操作的默认流程”“它的代价也明显”。

**A.2 的角色与职责必须逐项对应：**

| 角色 | 教程中的职责 |
|---|---|
| FOUNDER | 定目标、拍板、验收 |
| PLANNER | 拆需求、排优先级 |
| BUILDER / CODER | 实现 |
| QA | 验收与问题单 |
| OPS | 发布、备份、自动化 |
| MARKETER | 文案、渠道、增长实验 |

来源：第二段“它适合用来做”六项清单。`BUILDER / CODER` 为同一清单项，因此共 **6 项**。

需保留其理由：创始人同时承担多种角色，文件流程帮助拆分角色；即使执行者是同一个人加 AI，也可用 TASK／REPORT／ISSUE／log 留下意图、委派、结果和修改原因。  
来源：“创始人同时扮演太多角色”“即使背后都是同一个人 + AI”。

**A.3 的五项价值与两项注意事项：**

| 类型 | 必须保留的内容 |
|---|---|
| 价值 1 | 不同模型、会话、角色之间通过文件交接，不依赖聊天上下文 |
| 价值 2 | PM／DEV／QA／OPS／Docs／Security 的派单与回执权限有文件约束 |
| 价值 3 | 大需求拆分后，沿 `thread_key / parent` 追溯 |
| 价值 4 | 减少两个 Agent 同方向并发修改、互相覆盖和重复决策 |
| 价值 5 | 人类和 Agent 均可读文件继续工作，支持异步团队 |
| 注意 1 | FCoP 只管协作；需求池、排期、工单、权限、发布流水线仍应放在专业系统 |
| 注意 2 | 按团队、子系统、批次分层组织，不能全塞入一个 `docs/agents/tasks/` |

来源：第三段“大型项目里的价值主要是”及“要注意两点”。`dev-team/`、`qa-team/`、`inbox/outbox/`、`tasks/sprint-12/` 是目录示例，不是本次必须创建的目录。
