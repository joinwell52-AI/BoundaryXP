# 五组对照：逐案复核记录

本文件由开发代理对照预先固定的 cases.json、实际生成文本、独立审阅与真实查询记录整理，不是独立人工盲评。只衡量本组样本，不能把模型自评当作语义正确性证明。原文保真与字典增益分开；保留审阅指出的问题，不改写首次生成结果。

## DICT-01：专业操作区分

ui104 两组均保留十项预期边界：repo-a、review 分支、QA→PM→ADMIN交付链、交付完成条件、20分钟上限及四项禁止；均未把提交代码等同合并、发布或部署授权。

两组均无实际字典查询。没有可归因于 L2/L3 的词条增益。无库生成用“DEV承担受限代码操作”，有库用“DEV负责上述获准的代码操作”；对“仅可”的许可模态，最好仍统一表达为“获准的执行主体”，避免职责措辞被理解成必做义务。两次 ui104 审阅均未指出这一措辞风险；此前 ui103 的无库审阅曾指出同类问题，不用于替换本轮结果。

## DICT-02：唯一人员别名

两组十项原文边界均有表达。只有有库组实际查询后提供了 pm-01、dev-01、qa-01 三个准确身份及 /employees/2、/employees/0、/employees/1 来源。无库保留项目协调员、开发一号、测试一号的原称谓，是合理的能力边界，不能算漏抽原文。

有库生成及审阅各查询四次（其中《核查说明》未命中）；没有补出说明正文。两组都有“角色分工不得相互替代／主体与职责不得互换”的概括限制，原文仅明确了具体参与关系。应收窄到原文指定的动作和主体，避免增加通用禁令。有库审阅指出此点，无库审阅没有指出，反映审阅的一致性仍有限。

## DICT-03：同名别名

两组保留原文主体、核对→生成→交付关系、ADMIN收到即完成、10分钟、测试环境及禁令；均未凭岗位猜定某人。有库生成和审阅分别查询“小王”一次，准确给出 e101 王明/开发部和 e102 王岚/测试部，并引用 /employees/4、/employees/5。明确“测试环境”不能用来选定测试部人员。无库只能保留称谓和身份信息缺失。字典把模糊的身份缺失定位为两个具体候选，是可核验增益。

无库审阅额外指出“只读”可能表示只读访问或读取对象排他；这是文本解释的局部风险，与企业字典无关。有库生成保留“只读”原词，未自动加强为禁止读取一切其他文件。

## DICT-04：人员状态

两组均保留模型文件、报告交付、期限、测试环境和训练/修改/部署禁令；没有从算法研究岗位推导权限，也未将“不负责批准发布”转成发布授权。有库生成还明确“不负责”并不等于额外禁止。

但有库生成和审阅实际查询均为零，未给出小李→李研/e104，也未展示 inactive。字典预期未达到：现有“按需”规则未确保碰到企业别名时进行查询。这不是“字典中没有信息”，而是模型没有读取已有信息。无库没有该状态资料，不能因此扣原文保真分。

未查阅 inactive，也就不能用本例宣称系统已经通过“停用资料与ADMIN指派冲突处理”的验证；该能力仍未在本次实际运行中被触发。

## DICT-05：未收录的对象

两组都保留脱敏导出件与正式库本体的区别、测试环境、交付/完成条件、10分钟及三项禁止；都没有补造客户库实例、导出路径、核心模块清单。有库生成与审阅各查“运维一号”一次，正确增加 OPS-01/ops-01 与 /employees/3 来源。

本例没有实际查询客户库、核心模块等对象，不能把“原文已声明缺失，模型没有补造”说成“查词未命中处理已验证”。本轮实际未命中的是第2例《核查说明》，生成与审阅都保留未提供正文。两种证据分开记录。

## 综合判断

- 原文层：各组主要边界均保留，没有发现因字典而删除原文禁令或放宽授权；但许可/职责措辞和概括性“不得互换”仍需收紧，审阅意见存在波动。
- 字典层：第2、3、5例有可追溯身份增益；第1例没有必要查词；第4例应查而未查。五个有库样本中三个实际查询，不能写成字典自动生效。
- L2：十次生成/审阅中没有查询 software-ai。专业动作区分正确，但这主要体现模型已有理解。本轮不能证明行业包单独改善了质量。
- L3：实际命中和身份引用均与企业A文件相符，同名两候选未被猜选。这是本轮最明确的收益。
- 速度：所有生成均小于60秒。带字典平均生成25.3秒，无字典19.7秒；工具调用时需多轮上下文，回执累计输入token也增加。缓存命中和随机波动存在，不能据五对单次样本给出稳定因果耗时结论。
- 下一步只需明确企业别名触发查询的条件：已选L3时，遇到企业人员称谓、内部对象别名，应核对或明确记录未查询；不因为读懂“小李”这个称呼就视为已知企业身份。继续不整包加载、不按岗位授予权限、不增加全任务数学证明。本轮未据结果修改Skill或重跑选优。
