## 3. 核心修复：产物身份、产物使用依赖与事件时序分开

### 3.1 固定语义区别

- **明确事件顺序**：原文明确要求“生成完成后再复核”“更新后再交付”，应由LLM表达相应TEMPORAL/条件及准确事件和对象。存在“完成后”才能表达相应完成前提，不能省略。
- **本次产物的使用依赖**：原文要求产生一份报告并复核这份产物，需要保留哪次产生、哪份产物及哪项使用的关系。使用对象须与本次结果关联；这不自动等于“生产事件的所有工作彻底结束后，消费事件才能开始”。
- **只有身份相同**：一个路径被多次提及不证明同一版本；检查旧文件后覆盖、流式/部分结果、不同轮报告、多来源竞争不能被全局串行化。
- **没有来源支持的顺序**：普通并列动作、组织/协作关系、MENTION_ONLY引用、条件里的事件、被禁止的操作不能凭常识补成执行顺序或义务。

“产物使用依赖”不使用证明图的`requires`去冒充调度依赖。身份引用、技术证据依赖、产物流与事件时序必须各自有确定含义，不建立虚假循环证明。

### 3.2 最小实现方法

从当前图出发，不重建语义系统：

1. 明确的`RESULT(producer, artifact)`与同一身份上的用途关系可确定性形成“由谁产生、被谁用于什么”的关联索引，并引用原主张ID与来源。该索引本身不追加硬时序。
2. 只有候选已表达“该使用针对本次产生的结果/相应版本”并且来源、身份及用途技术检查成立，才能按已文档化的规则形成产物可用性依赖；若现有图不足以表达这一前提，增加最少的用途/版本关联字段，由LLM识别并提交，程序不能靠文件名、谓词词表或自由文本note补造。
3. 明确时序仍消费LLM给出的结构；允许语义等价的边或可验证派生，不要求每个答案都长成同一组节点。
4. 派生关系标记DERIVED，包含规则版本、输入主张、对象身份、适用条件与来源路径；保持现有模态和作用域。不可把“允许生成”变成“必须生成”，不可把“产物可用”变成“QA已批准”。
5. 若对象/版本真的不确定，仅将相关依赖保持未决，不否定独立动作；若源文明确但模型未表达，反馈真实缺口给现有有界修订，不标ABSENT。
6. 可计算的关联必须进入IR/JSON，并在中文中保留差别；不能只写在note或审阅reason中。
