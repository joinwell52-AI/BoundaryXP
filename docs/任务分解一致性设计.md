# 界痕 · BoundX：PM 任务分解一致性计算

> 历史／非规范研究或产品规划（legacy / non-normative）。本文中的旧接口、原始结果和未来能力不代表当前产品合同或本轮验证；当前入口以根 README 和产品手册为准。No BXP extraction certification or execution authority is implied.

状态：任务分解的设计说明。当前实现及支持边界见 [分解接口](DECOMPOSITION.md)；本文不增加业务授权，不自动触发宿主执行。

后续实现说明：本设计的有限布尔契约部分已落地为独立 `reviewDecomposition` 接口；本文保留为设计记录，实际能力与限制以 [当前使用手册](DECOMPOSITION.md) 为准。

## 要回答的问题

PM 拆分任务之后，需要核查三件不同的事：原要求是否有人落实；全部子任务完成是否足以交付原任务；拆分是否增加了没有解释依据的动作或完成前提。依赖图无环只能说明一种结构性质，不能回答上述问题。

## 输入：原要求、派单契约、对应关系

原任务要求集合记为 R，每条要求有稳定 ID、原文引用和版本。每个子任务提供输入条件、承诺产出、完成条件、动作及所依赖的产物。对应关系应区分“直接落实某要求”和“为另一子任务提供必要支持”，并携带说明与原文依据。

例如根任务要求检查 FCoP、MCP、SKILLS、角色权限、轨道机运行，并向 ADMIN 汇报。将其映射成六项可核查义务，不能仅把“汇报”理解成每位成员各自写文件；“向 ADMIN 汇总交付”应根据原文单独说明。

这些映射由调用方提供并交相应责任人核查。标识关联只是声明，不是证明；同义表达、合理准备工作和证据不足必须保留待核查状态。

## 计算一：追溯覆盖

设 Mᵢⱼ = 1 表示子任务 j 声明落实原要求 i。若某行之和为零，则该原要求尚无声明承担者：

    Missing = { rᵢ ∈ R | Σⱼ Mᵢⱼ = 0 }

这里统计的是追溯关系覆盖，不是实际完成率。即使每行都有 1，也可能没有充分产出。多个子任务共同落实同一要求时，必须说明它们是全部必需还是可相互替代，不能由矩阵自行推断。

反方向，子任务既无直接对应要求，也无通向原交付的已说明支持关系时，返回“必要关系待解释”，不能机械删除该任务。建立测试环境等工作可能是合理细化。

## 计算二：局部完成是否足以整体交付

设 C₀ 为原任务完成谓词，Cⱼ 为第 j 项必需子任务完成谓词，D 为已经显式声明并核查的业务关系。在所有子任务都必需的简化模型中，P = C₁ ∧ … ∧ Cₙ。存在可选分支时必须显式提供组合表达式 P，不能继续一律取逻辑与。

先检查 D ∧ P 是否可满足。若不能满足，说明当前模型下子任务无法一起完成，不得因为后续找不到反例而宣称分解正确。

然后查找：

    D ∧ P ∧ ¬C₀

若存在赋值，就得到“所有子任务均完成，原任务仍未完成”的具体反例。若不可满足，只能说在所给映射与 D 下，P 蕴含 C₀；不证明自然语言理解正确或真实执行一定成功。若映射缺失、求解超时或方法不支持，返回无法判断，不能当作没有异常。

### 具体代入

设 a、b、c 分别表示三份检查证据已按约定完成，其中第一份覆盖 FCoP/MCP，第二份覆盖 SKILLS/角色权限，第三份覆盖轨道机。设 h 表示汇总报告已向 ADMIN 交付。

    C₀ = a ∧ b ∧ c ∧ h

PM 只派了三份检查，没有安排汇总交付，因此：

    P = a ∧ b ∧ c

在没有其他已确认业务关系时，D 为真。代入 a=b=c=真、h=假：P 为真而 C₀ 为假。提醒应为：“三份检查均可完成，但没有明确的汇总交付承担者或交付条件。请说明已有安排，或完善规划。”

若 PM 增加汇总义务 h，P 变成 a ∧ b ∧ c ∧ h，该示例中的缺交付反例消失。义务可以由 PM 本人承担，不强制要求新建一张子任务单。

## 计算三：额外完成前提与额外动作

在子任务内部执行状态与原任务成果使用共同状态空间、且对应关系已经表达的前提下，查找反向差异：

    D ∧ C₀ ∧ ¬P

例如在完整规划中又加入 f（修复通过），P = C₀ ∧ f。取 C₀ 为真、f 为假，会发现原要求已满足但新规划不允许完成。

这个方向尤其不能直接认定越权：合理的内部实现步骤也可能比原成果谓词更具体。工具应展示新增前提及来源，要求 PM 说明其必要性或授权依据，不强制所有内部步骤与根任务严格等价。必要时需将内部状态投影到共同交付变量再比较；该投影机制需要单独实现和验证。

交付条件未变化也可能出现额外写代码动作，因此还必须单独比较动作和允许范围。完成逻辑不能代替动作授权核查。

## 计算四：子任务接口是否接得上

依赖边必须说明等待哪项产物、哪个版本、需要满足什么条件，而不只是 task ID。对下游 j 的输入条件 Preⱼ，使用已声明的上游保证 Upⱼ 和外部输入条件 Extⱼ，查找：

    D ∧ Upⱼ ∧ Extⱼ ∧ ¬Preⱼ

存在反例表示上游即使兑现承诺，也可能不足以支持下游开始。例如 DEV 只承诺“问题数量”，QA 却要求“复现步骤与日志”。工具应指出缺失接口并建议明确责任，不能凭同一个“报告”标签认定输入齐备。

这仍是契约检查，不是实际资源调度或无死锁证明。现有未知节点与有向环检查继续作为独立检查保留。

## 输出与不裁决

每条发现包含原要求 ID、相关子任务与引用、采用的假设、反例赋值或缺失关系、具体建议以及待核查原因。负责人可以修正、解释不采纳或请求授权方澄清。界痕记录回应完整性；提醒送达、催办、授权申请流转由宿主负责。

不把所有维度加权成未经校准的“理解分数”，不把逻辑不可满足当作业务拒绝权。结果区分发现反例、在当前模型下未发现反例、无法判断。

## 实现与测试计划

当前接口只有 document、tasks 和 depends_on，缺少上述要求追溯、契约和逻辑组合字段，因此本设计尚未实现。下一次内核开发应先登记变更基线与固定测试协议，再扩展兼容接口。

预定案例包括：缺少原要求承担者；关联齐全但没有保证产出；遗漏汇总交付；合理准备任务；新增修复前提；新增动作但不改完成条件；上游输入不足；可选分支；业务关系排除假反例；矛盾模型造成空真；未知依赖与有向环；缺失映射或求解未知。

有限布尔域可先用独立穷举核验逻辑结果，再评估求解器接入。测试算法正确性与测试模型是否因此改善必须分别记录，固定案例数量不能称为 Agent 实验次数。

上述“检查蕴含的反例是否可满足”属于标准命题逻辑方法，参考 [Z3 官方命题逻辑指南](https://microsoft.github.io/z3guide/docs/logic/propositional-logic/)。本文没有声称已经集成 Z3，也不主张基础逻辑方法的原创性。
